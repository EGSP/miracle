# Анализ заказа

Папка содержит джобы анализа заказа. Сейчас существуют **две версии алгоритма**. Первая
остаётся как есть, вторая — новая и описана здесь подробно. Версии независимы и запускаются
разными корневыми джобами; общего у них только этап чтения приложений.

## Словарь

- **Заказ** — то, что анализируем. У заказа есть приложения.
- **Приложение (заявка)** — исходный документ заказа (файл/текст). Из него извлекаются позиции.
- **Позиция** — одна заказная единица: продукт + связный набор требований. У позиции есть
  дословное название, (опционально) тип продукции из справочника и список требований.
- **ТУ (Техническое Условие)** — документ с правилами, по которым строится условное обозначение
  продукции данного типа. Состоит из **слотов** и поля **примеров расшифровки**.
- **Слот** — один параметр условного обозначения (например, «Климатическое исполнение»). У слота
  есть индекс (позиция в обозначении) и текст правил выбора значения из ТУ.
- **Условное обозначение** — итог анализа позиции: значение по каждому слоту своего ТУ.

## Зачем нужна вторая версия

В первой версии каждая позиция анализировалась изолированно: на одну позицию уходил один запрос,
куда вкладывались системный промпт + информация о позиции + **полное ТУ целиком**. Системный
промпт и полное ТУ занимали бóльшую часть запроса. Когда позиция — это короткая строка с шифром
и одним требованием, КПД запроса низкий: токены тратятся непропорционально размеру заявки. Для
заказа с десятками однотипных позиций полное ТУ улетало в модель десятки раз.

Вторая версия бьёт по двум направлениям:

1. **Группировка однотипной продукции.** Позиции одного ТУ обрабатываются вместе. Системный
   промпт и правила амортизируются на всю группу, а не повторяются на каждую позицию. Это и есть
   основная экономия токенов.
2. **Пошаговый анализ по слотам.** Один запрос = один параметр условного обозначения. Вместо
   полного ТУ в запрос идёт только правило текущего слота (плюс примеры расшифровки из ТУ).
   Пошаговость экономит не токены, а:
   - **точность** — модель получает одну точную инструкцию и не распыляется на всё обозначение;
   - **размер ответа** — ответ на шаг ограничен (позиции группы × один слот), он маленький и
     надёжно парсится; один гигантский ответ «всё ТУ × все позиции» рисковал упереться в лимит
     вывода и вернуть хрупкий JSON;
   - **наблюдаемость** — результат шага сразу пишется в базу, обозначение собирается на глазах.

> Важно понимать размен: вторая версия **дешевле по токенам и точнее**, но **медленнее по
> времени**. Первая версия гнала все позиции параллельно; вторая идёт группами и внутри группы —
> слот за слотом, последовательно (ограничения Яндекс-сервиса). Это осознанный размен.

## Порядок действий (этапы)

### Этап 0. Запуск и переиспользование

Анализ заказа запускается со стабильным ключом корневого прогона. Повторный анализ **той же
версией алгоритма не должен заново платить за извлечение позиций**: этап чтения приложений
адресуется ключом, не зависящим от конкретного запуска анализа заказа. При повторе джоб находит
уже завершённый прогон приложения и берёт готовый результат, не вызывая LLM повторно. Принудительное
переизвлечение (если приложения изменились) — отдельный явный шаг, который сносит прежние прогоны
приложений.

Деструктивные операции переанализа (снос прежнего дерева прогонов, чистка данных) живут на
триггер-слое, а не в теле джоба — тело остаётся replay-safe.

### Этап 1. Анализ приложений → позиции

Без изменений относительно первой версии. По каждому приложению заказа читается подготовленный
документ, бьётся на чанки, из каждого чанка извлекается список позиций (сегментация, классификация
типа продукции по справочнику, дословный захват требований). Позиции пишутся в базу. Этап
best-effort: упавшее приложение/чанк не валит остальные.

Результат этапа — позиции заказа в базе. Дальше работают только позиции, у которых определён тип
продукции (для остальных условное обозначение строить не из чего).

### Этап 2. Группировка позиций

1. Берём все позиции заказа с определённым типом продукции.
2. Для каждого типа резолвим ТУ. Гейты выносятся **сюда**, на формирование групп (в первой версии
   они были внутри пер-позиционного джоба):
   - тип → ровно одно ТУ → позиция попадает в группу этого ТУ;
   - тип → ноль ТУ или несколько ТУ (неоднозначно) → позиция не группируется и попадает в отчёт
     как ошибка с понятным сообщением (вся такая «группа» падает, остальные продолжаются).
3. Группа — это `tcId` + список позиций этого ТУ.
4. **Разбиение больших групп на подгруппы.** Если суммарный размер требований группы превышает
   порог токенов, группа делится на несколько подгрупп. Подгруппа — это **не новая сущность**: это
   просто ещё одна группа с тем же `tcId`, но с другим подмножеством позиций. Порог задаётся
   константой и по умолчанию выключен (см. «Тумблеры»).

### Этап 3. Пошаговый анализ группы

Группы обходятся **последовательно** (ограничения Яндекса; см. «Тумблеры» про возможный параллелизм).
Каждая группа обрабатывается так:

1. Фиксируется **детерминированный порядок позиций** группы (сортировка по стабильному ключу —
   id позиции). Позиции получают **локальные индексы** внутри группы: `0, 1, 2, …`. В запрос к
   модели идут именно локальные индексы (короткие, модель надёжнее их эхо-ит, и токенов меньше),
   а соответствие «локальный индекс → id позиции» хранится на нашей стороне.
2. Слоты ТУ обходятся **по порядку индекса, по одному за запрос**. На каждый слот:
   - в модель отправляется: правило **только этого слота** + примеры расшифровки из ТУ + массив
     позиций группы (локальный индекс → название + требования);
   - модель возвращает по одному ответу на каждую позицию: `{ локальный индекс, значение или null,
     уверенность (enum), обоснование }`;
   - ответ маппится обратно на id позиций, и значение каждого слота **сразу пишется в базу**
     (точечное обновление одного слота обозначения позиции).
3. Когда все слоты пройдены — обозначения всех позиций группы собраны.

Между шагами в модель **не подаются результаты предыдущих шагов** — каждый слот определяется
независимо по названию и требованиям позиции. (Почему — см. «Отложенные идеи».)

### Свод результата

Исход каждой группы и каждого приложения сводится в общий статус заказа: всё успешно → `succeed`,
часть упала → `partial`, всё упало → `failed`. Частичный успех не теряется под обёрткой ошибки.

## Консистентность и возобновление (кто на чём остановился)

Алгоритм должен переживать рестарт и не платить дважды за уже сделанную работу. Состояние
запоминается на двух уровнях:

- **Уровень джоба (группа).** Каждая группа — отдельный дочерний прогон с собственным стабильным
  ключом. При возобновлении уже завершённая группа переиспользуется целиком, не запускается заново.
  Группа — видимый узел в дереве прогонов с собственным прогрессом.
- **Уровень инструмента (слот).** LLM-вызов одного слота — это **JobTool** с durable-памятью.
  Идентификатор облачной операции (`opId`) сохраняется в память инструмента **до** ожидания ответа
  (паттерн submit-once). При рестарте инструмент не отправляет запрос повторно, а продолжает опрос
  уже существующей операции. Готовый разобранный ответ слота тоже кэшируется в памяти инструмента.

Запись слота в базу **идемпотентна** (точечный merge по индексу слота): повторное применение того
же результата ничего не ломает. Поэтому связка «инструмент закэшировал ответ» + «запись в базу
идемпотентна» даёт полное возобновление без двойных списаний за LLM.

**Стабильность локальных индексов** критична для возобновления: соответствие «локальный индекс →
id позиции» не хранится в памяти, а **восстанавливается детерминированно** — той же сортировкой
позиций группы по id. При рестарте сортировка даёт тот же порядок, поэтому локальные индексы и id
позиций совпадают с тем, что было до перезапуска.

## Изменение схем: уверенность как enum

Числовая уверенность `0..1` заменяется на перечисление `high | medium | low`. Числовая шкала от
модели — ложная точность: всё равно загонялась в пороги и шумела. Перечисление честнее и убирает
магические константы из кода подсветки.

- Подсветка ячеек обозначения строится по enum: `low` → критично, `medium` → предупреждение,
  `high` → без подсветки. Незаданное значение (`null`) — предупреждение независимо от уверенности.
- Рефактор затрагивает общий слой отображения обозначения и его зеркало на фронте, инспектор
  обозначения, карточки позиции и отчёты.

Образец уже есть: уверенность сегментации позиции (`high | medium | low`) на этапе извлечения.

## Тумблеры (константы алгоритма)

Часть поведения вынесена в константы. Значение по умолчанию подобрано так, чтобы новое поведение
было выключено — включается осознанно.

- **Порог токенов для разбиения группы** — `number | undefined`, по умолчанию `undefined`
  (разбиение не применяется, группа = все позиции одного ТУ). Для подсчёта используется примерный
  счётчик токенов из общих типов.
- **Параллелизм групп** — по умолчанию последовательно. Константа на случай, если Яндекс позволит
  ограниченный параллелизм; пока эффективно выключена.
- **Параллелизм слотов** — по умолчанию последовательно (всё равно упрётся в Яндекс). Константа
  заведена «на будущее» и пока не работает.

## Отложенные идеи

Идеи, которые обсуждались и осознанно отложены — чтобы вернуться позднее, а не потерять.

- **Подача результатов предыдущих шагов в контекст слота.** Сейчас каждый слот независим. Если на
  практике всплывут ошибки на взаимозависимых параметрах, можно точечно подавать в шаг только
  нужный предыдущий слот. Блансетом подавать все прошлые результаты не стоит — это возвращает рост
  запроса и съедает выигрыш группировки.
- **`dependsOn` на уровне слота ТУ.** Явное объявление зависимостей между слотами (какой слот
  нужен для вычисления другого). Пара к предыдущему пункту. Пока не вводим.
- **Параллельная обработка слотов и групп.** Слоты в основном независимы, поэтому строгий порядок
  им не нужен по корректности — только из-за лимитов Яндекса. Если лимиты позволят, ограниченный
  параллелизм сократит время. Тумблеры заведены, но выключены.
- **Название позиции как сильный сигнал.** Дословное название часто уже содержит шифр/обозначение.
  Это дешёвый и ценный сигнал — его имеет смысл всегда подавать в шаг вместе с требованиями.
