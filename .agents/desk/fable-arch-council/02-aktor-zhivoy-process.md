# Архитектор «Актор»: разговор — это долгоживущий процесс

> Оптимизируемые качества: **живость диалога (перебивания, промежуточные сообщения,
> напоминания), естественность для Effect, минимум новых таблиц.** Цена: середина хода
> не переживает перезапуск; всё исполняется в одном процессе.

## Исходный тезис

Разговор — не данные и не джоба. Разговор — это **процесс, который живёт**, пока живо
внимание пользователя. У процесса есть очередь входящих сообщений, и всё происходящее
в мире выражается сообщением в эту очередь: реплика пользователя, завершение джобы,
срабатывание таймера, команда отмены. Процесс сам решает, как поступить с каждым
сообщением, — в этом заключается вся модель. Не существует отдельных задач «одновременная
переписка», «прерывание», «напоминание»: есть один примитив — сообщение.

Коллеги возводят соборы: журнал с воспроизведением, компилятор с собственным языком.
Я же предлагаю то, что Effect умеет из коробки: волокно (fiber), очередь (Queue),
область времени жизни (Scope). Это кратчайший путь к диалогу, который *ощущается* живым.

## Устройство

Одна доска — один актор: Effect-волокно с циклом приёма сообщений. Реестр держит живые
акторы, пробуждает спящие по требованию и усыпляет бездействующие по истечении срока.

```ts
type BoardMsg =
  | { _tag: 'UserMessage'; text: string; idempotencyKey: string }
  | { _tag: 'Command';     fn: string; args: unknown; idempotencyKey: string }  // программный вход (интерфейс, 1С) — без модели
  | { _tag: 'JobDone';     jobRunId: string; outcome: JobOutcome }              // пришло мостом из фреймворка задач
  | { _tag: 'Timer';       timerId: string }                                    // напоминания, сроки подтверждений
  | { _tag: 'Interrupt' };                                                      // «стой, это не то»

// Актор: плоский цикл приёма. Вложенности нет — каждый обработчик возвращает новое состояние.
const boardActor = (boardId: BoardId) =>
  Effect.gen(function* () {
    const mailbox = yield* Queue.unbounded<BoardMsg>();
    let state = yield* loadSnapshot(boardId);          // DialogState вместе со списком незавершённых работ — из БД
    while (true) {
      const msg = yield* Queue.take(mailbox);
      state = yield* handle(state, msg);               // обработчик может ответвлять работу (см. ниже)
      yield* saveSnapshot(boardId, state);             // снимок состояния после КАЖДОГО перехода
      yield* appendTurns(boardId, state.emitted);      // лента ходов для интерфейса и 1С пишется отсюда
    }
  });
```

**Главное отличие от варианта «ход-джоба»:** ход не удерживает актора. Долгая функция
ответвляется в отдельное волокно, а актор немедленно освобождается:

```
UserMessage("проанализируй заказ")
  → обработчик: маршрутизатор (модель) → analyzeOrder → jobs.run(...) ОТВЕТВЛЯЕТСЯ
  → в состояние записывается { jobRunId, черновик будущего ответа }
        (и сохраняется в снимке — это однократная отправка на уровне актора)
  → немедленный ответ «Запустил анализ…»           ← актор СВОБОДЕН
UserMessage("а покажи вторую позицию")             ← обрабатывается сразу, анализа не дожидаясь
  → ответ карточкой позиции
JobDone(jobRunId)                                  ← доставлено мостом уведомлений
  → ответ «Анализ готов: 12 позиций, 2 требуют внимания»
```

Одновременная переписка, сообщения о ходе долгой работы, команда «стой» (`Interrupt` →
прерывание ответвлённого волокна), таймер «срок подтверждения истёк» — всё это выражается
**одним и тем же циклом приёма**, без отдельного механизма на каждый случай.

## Изменения во фреймворке задач

1. **Мост уведомлений о завершении** (единственная правка; разведочный прототип S2):
   после завершения `JobRun` выполняется `NOTIFY job_done` (механизм LISTEN/NOTIFY
   в PostgreSQL) либо публикация во внутрипроцессную шину. Один слушатель на процесс
   раскладывает уведомления по очередям акторов согласно спискам незавершённых работ.
   Без моста актору пришлось бы опрашивать базу — это разрушило бы модель.
2. Джобы, `Swarm`, `ToolMemo`, учётная книга токенов — без изменений. Актор —
   потребитель фреймворка, а не его замена.

## Устойчивость: снимки состояния, с честным признанием слабости

Истина о состоянии — **снимок после каждого перехода** плюс лента ходов. Промежуточные
шаги внутри одного обработчика по отдельности не сохраняются:

- Падение посреди многошагового обработчика означает, что сообщение осталось
  неподтверждённым; при пробуждении актора оно обрабатывается заново, и решения модели
  запрашиваются повторно (недетерминизм!). Однако: запуск джоб идёт через
  `jobs.run` со стабильным ключом — повторный вызов присоединяется к уже идущему
  запуску, двойной оплаты не происходит; правки состояния оформляются идемпотентными
  поправками.
- Это осознанный размен: **простота модели против точности возобновления.** Для реплик
  длительностью в секунды окно возможной потери ничтожно; долгая работа делегирована
  джобам, которые устойчивы по-настоящему.
- Если окно потерь окажется болезненным, внутрь обработчика можно точечно добавить
  упреждающую запись решений маршрутизатора в снимок (заимствование у Летописца),
  не меняя модель в целом.

## Диалог как основной интерфейс и интеграция с 1С

REST-слой тонок: `POST /boards/:id/messages` кладёт сообщение в очередь (при
необходимости пробуждая актора) и возвращает `202`; ответы читаются из ленты ходов
(`GET /boards/:id/turns?after=`, опрос либо SSE). Идемпотентность обеспечивается
хранением последних K ключей в снимке. Команды от 1С — сообщения `Command` в ту же
очередь, минуя модель.

Таймеры дают качество, недоступное остальным предложениям: доска способна **проявить
инициативу** — например, сама написать в 1С, что срок подтверждения по заказу истекает.
Сервис перестаёт быть только отвечающим.

## Слабые стороны (называю сам)

1. **Середина хода не переживает перезапуск** (см. выше) — главный размен предложения.
2. **Один процесс.** Акторы живут в памяти одного экземпляра сервиса. Для прототипа
   и обозримой нагрузки этого достаточно; горизонтальное масштабирование потребует
   либо привязки досок к экземплярам, либо переноса истины в журнал — то есть двери
   к Летописцу.
3. **Надзор пишем сами:** пробуждение по требованию, усыпление, ограничение числа
   одновременно живых акторов, поведение при переполнении очереди. По объёму это
   порядка двухсот строк, но это наши двести строк.
4. Проверять цикл приёма испытаниями сложнее, чем чистую свёртку Летописца: нужны
   управляемые очереди и время (у Effect для этого есть TestClock — терпимо).

## Что стоит позаимствовать, даже если моё предложение отклонят

- **Мост уведомлений о завершении джоб** — необходим любой архитектуре, включая базовую
  линию: без него сообщения о ходе долгой работы требуют опроса базы данных.
- **Принцип «всё — сообщение»** как модель мышления о прерываниях и таймерах: даже
  в варианте «ход-джоба» политику прерывания проще всего выразить сообщением,
  а не флагом в таблице.
- **Усыпление бездействующих досок** — понадобится всякому решению, в котором доска
  хоть что-то держит в памяти процесса.
