# Архитектор «Летописец»: разговор — это журнал событий

> Оптимизируемые качества: **аудируемость, воспроизводимость, диагностика, надёжный
> интеграционный контракт.** Цена: строгая дисциплина работы с проекциями и непривычная
> парадигма.

## Исходный тезис

Текущее состояние системы — это краткий пересказ её прошлого, и, как всякий пересказ,
он теряет подробности. В диалоговой системе с недетерминированным участником (языковой
моделью) единственный способ ответить на вопросы «почему система приняла такое решение»,
«что в этот момент видел пользователь», «как воспроизвести ошибку» — записывать не итоговое
состояние, а **каждое произошедшее событие**, и выводить состояние из журнала вычислением.
Такой подход известен как событийное хранение (event sourcing).

Замечу: проект уже наполовину устроен именно так. `ToolMemo` — это журнал контрольных
точек; приём однократной отправки — это запись решения до его исполнения. Я предлагаю
довести идею до логического завершения и получить **одну** модель хранения вместо трёх
(лента ходов, память джобы, память инструментов).

## Устройство

Всё хранится в одной таблице, пополняемой только добавлением:

```sql
boards          (id, order_id, created_at)
board_events    (id, board_id, seq BIGINT, turn_index INT,
                 type TEXT, payload JSONB, created_at,
                 UNIQUE (board_id, seq))
-- кэш свёртки, чтобы не пересчитывать состояние с начала журнала:
board_snapshots (board_id, upto_seq, state JSONB)
```

Перечень типов событий — закрытое объединение; по сути, это и есть схема системы:

```ts
type BoardEvent =
  | { type: 'user_message';    text: string; idempotencyKey: string }
  | { type: 'command';         fn: string; args: unknown; idempotencyKey: string } // программный вход (интерфейс, 1С)
  | { type: 'router_decided';  step: number; fn: string; args: unknown }   // решение модели, записанное ДО исполнения
  | { type: 'function_done';   step: number; resultRef: unknown }          // краткий результат; объёмное — по ссылке
  | { type: 'job_triggered';   step: number; jobRunId: string }
  | { type: 'job_finished';    jobRunId: string; outcome: 'succeed'|'partial'|'failed' }
  | { type: 'state_patched';   patch: StatePatch }                         // правки позиций и подобное
  | { type: 'status';          text: string }                              // промежуточное сообщение хода
  | { type: 'replied';         text: string }
  | { type: 'await_user';      prompt: string; pending: PendingConfirm };

// Состояние доски — чистая функция от журнала:
const foldState = (events: BoardEvent[]): DialogState => events.reduce(applyEvent, initialState);
```

Обработка хода — тот же трамплин, что и в базовой линии, однако памятью трамплина служат
**события текущего хода**:

```
в начале хода: состояние = снимок + свёртка событий, записанных после снимка
шаг N:
  1. Есть ли в журнале событие router_decided с номером N?
        есть → взять решение из журнала (воспроизведение);
        нет  → обратиться к модели → записать router_decided ДО исполнения.
  2. Есть ли событие function_done с номером N?
        есть → шаг уже исполнен, пропустить;
        нет  → исполнить функцию → записать function_done.
  3. Достигнуто завершение → записать replied либо await_user.
```

В диалоговом слое не нужны ни `Memo`, ни `ToolMemo`: **журнал одновременно служит лентой
для интерфейса, памятью для возобновления и трассой для аудита.** Три задачи закрываются
одной таблицей.

## Изменения во фреймворке задач (допустимы: стадия прототипа)

- Диалоговый слой не пользуется полем `JobRun.memo` вовсе. Существующие джобы (анализ,
  распознавание) **не изменяются** — они продолжают работать со своей памятью.
- Добавляется мост: при завершении `JobRun` дополнительно записывается событие
  `job_finished` в журналы досок, подписанных на данный запуск (простая таблица подписок
  либо метка в самом запуске). Это разведочный прототип S2 из `00-sobranie.md`;
  он необходим всем архитектурам собрания.
- Радикальное направление на будущее (не сейчас): перевести на события и память самих
  джобов — тогда весь наблюдательный контур системы (дерево запусков, статистика,
  выгрузка в Langfuse) будет читать единый журнал. Фиксирую как направление, не как
  требование.

## Диалог как основной интерфейс и интеграция с 1С

Журнал **сам является интеграционным API** — отдельный протокол не требуется:

```
POST /boards/:id/commands   { text | {fn,args} },  заголовок Idempotency-Key
  → добавление события user_message либо command → 202 { seq }
GET  /boards/:id/events?after=<seq>        (периодический опрос либо SSE)
  → хвост журнала: статусы, ответы, запросы подтверждения — внешняя система просто читает события
```

Идемпотентность повторных запросов от 1С достаётся даром: уникальный индекс
`(board_id, idempotencyKey)` на командных событиях превращает повторную отправку того же
сообщения в пустую операцию с прежним номером. Для интеграции с внешней системой это
не мелочь: устойчивость к повторам запросов — половина надёжности всего контракта.

## Отказы и восстановление

- Падение на любом шаге хода: при перезапуске свёртка журнала восстанавливает и состояние,
  и позицию трамплина; решения модели не запрашиваются повторно, поскольку записаны.
  Это строго сильнее и варианта «ход-джоба» (где память рассеяна между `Memo` и
  `ToolMemo`), и снимков Актора.
- Диагностика с «путешествием во времени»: отчёт об ошибке — это идентификатор доски
  и диапазон номеров событий; журнал можно свернуть локально до любого момента и увидеть
  ровно то, что видел маршрутизатор. Для системы с недетерминированным участником это
  самый дешёвый способ отвечать на вопрос «почему».
- Langfuse сохраняется (трассы обращений к модели через порт `LlmUsageSink`), однако
  для продуктового аудита достаточно уже самих событий, без внешнего сервиса.

## Слабые стороны (называю сам)

1. **Дисциплина проекций.** Состояние разрешено читать только через свёртку либо снимок.
   Одно «быстро прочитаю боевую таблицу напрямую» — и проекция начинает лгать.
   Смягчение: позиции заказа в журнал доски **не входят** — они живут в своих таблицах,
   как и прежде; журнал доски охватывает только разговор и его решения. Граница узкая
   и честная.
2. **Эволюция схемы событий.** Переименование поля в полезной нагрузке делает старые
   журналы несворачиваемыми. Смягчение: версия в имени типа (`router_decided.v1`) —
   тот же приём, что версии в типах `JobTool`.
3. **Непривычность.** Событийное хранение — парадигма, а не библиотека; мыслить
   событиями нужно начать до написания кода.
4. **Рост журнала** на объёмах чата не страшен (сотни событий на доску), однако снимки
   необходимы с первого дня — иначе свёртка длинных досок станет ощутимой.

## Что стоит позаимствовать, даже если моё предложение отклонят

- **Запись решения модели как события до его исполнения.** Это сильнее записи в
  `ToolMemo`: решение видно в той же ленте, которую читает интерфейс.
- **Ключ идемпотентности на входной команде** — обязателен для интеграции с 1С при
  любой архитектуре.
- **Событийная форма ленты ходов** (типизированные записи вместо просто «сообщений») —
  недорого сейчас и оставляет открытой дорогу к полному журналу.
