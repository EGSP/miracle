# Архитектор «Компилятор»: намерение — это программа

> Оптимизируемые качества: **наибольший детерминизм, наименьшее число обращений к модели
> (расход токенов, задержки), проверяемость до исполнения, язык программ как
> интеграционный API для 1С.** Цена: ставка на способность YandexGPT к компиляции
> и трудозатраты на проектирование языка.

## Исходный тезис

Языковая модель — плохой исполнитель, но неплохой компилятор. Коллеги оставляют модель
**внутри цикла исполнения**: каждый шаг их трамплинов — вероятностная развилка, и вся
их машинерия устойчивости — журналы, снимки, упреждающая запись — обслуживает
недетерминизм, который они сами же и впустили в исполнительный контур.

Предлагаю исключить модель из контура полностью. Одна реплика пользователя →
**одна компиляция** в небольшую типизированную программу → проверка → при разрушающих
действиях — показ программы пользователю → исполнение детерминированным интерпретатором
**без единого обращения к модели внутри**.

Проект уже мыслит в этом направлении: документ `order/README.md` прямо возражает против
«одного огромного агентного вызова» и настаивает на пошаговости и малых проверяемых
ответах. Я лишь переношу тот же принцип с конвейера анализа на диалог.

## Язык программ: шесть операций, и ни одной больше

Программа — это данные (JSON), а не код. Жёсткое правило: словарь операций не растёт
(принцип «сдерживай словарь» из `08-principy.md`).

```ts
type Prog =
  | { op: 'call';  fn: string; args: unknown; bind?: string }   // вызов функции; результат — в переменную
  | { op: 'seq';   steps: Prog[] }                               // последовательность
  | { op: 'if';    cond: Cond; then: Prog; else?: Prog }         // ветвление по уже вычисленным переменным
  | { op: 'ask';   prompt: string; bind: string }                // вернуть ход пользователю и ждать ответа
  | { op: 'reply'; template: string }                            // ответ с подстановкой значений {переменная.путь}
  | { op: 'fail';  message: string };                            // компилятор признаёт, что команду выполнить нельзя

// Условие — декларативное сравнение, не выражение языка:
type Cond = { var: string; path?: string; op: 'eq'|'gt'|'exists'|'empty'; value?: unknown };
```

Пример. Команда «Перебей материал во второй позиции на 12Х18Н10Т и переанализируй
обозначения» компилируется в:

```json
{ "op": "seq", "steps": [
  { "op": "call", "fn": "editPosition",        "args": { "ref": "#2", "field": "material", "value": "12Х18Н10Т" } },
  { "op": "call", "fn": "analyzeDesignations", "args": { "scope": "order" }, "bind": "run" },
  { "op": "reply", "template": "Материал обновлён, анализ запущен ({run.status})" }
]}
```

Компиляция выполняется структурированным выводом по JSON-схеме программы. Полученная
программа сохраняется по принципу однократной отправки — это **единственная** точка
недетерминизма во всём цикле. Если Yandex не справится с рекурсивной схемой, применяется
плоская кодировка: нумерованный список шагов с необязательным охранным условием `when`
у каждого шага, без вложенности; семантика та же, а схема тривиальна.

## Проверка и подтверждение — до исполнения

Скомпилированная программа проходит статическую проверку обычным кодом, без модели:
каждая функция `fn` существует в реестре; аргументы проходят Zod-схему соответствующей
функции; каждая используемая переменная определена раньше по ходу программы; глубина
и размер ограничены. Невалидная программа возвращается компилятору на одну
перекомпиляцию вместе с перечнем ошибок — так же, как компилятор возвращает
диагностику; после второй неудачи — операция `fail`.

Если программа содержит функцию, помеченную как разрушающая (повторный анализ уничтожает
позиции), исполнение не начинается: программа **отображается пользователю в виде
человекочитаемого плана** («1. Изменю материал… 2. Запущу повторный анализ — текущие
обозначения будут пересчитаны. Подтвердить?») и ждёт согласия. Подчеркну: подтверждение
разрушающих действий здесь не заплатка, а естественное свойство модели — ни Летописец,
ни Актор не могут показать намерение системы до его исполнения.

## Интерпретатор — одна универсальная джоба

```ts
type ProgMemo = {
  program?: Prog;                  // однократно сохранённый результат компиляции
  pc?: number;                     // счётчик текущего шага (для плоской кодировки)
  env?: Record<string, unknown>;   // значения переменных; краткие, объёмное — по ссылке
  compileCount?: number;           // число компиляций (предел — две)
};
```

`RunProgramJob` — обычная джоба фреймворка. Каждая операция `call` идёт через
существующие механизмы (`JobTools.run` либо `Jobs.run` со стабильным ключом — с
присоединением к идущему запуску, однократной отправкой и учётом токенов, как везде).
Возобновление тривиально и **точно**: в памяти лежат программа и позиция, а поскольку
в исполнении нет недетерминизма, нет и проблемы воспроизведения. Середина хода устойчива
по построению — то, что Актор отдаёт, а Летописец покупает ценой дисциплины, мне
достаётся даром.

Операция `ask` завершает джобу состоянием «ждёт пользователя», сохранив продолжение
(программу, счётчик, переменные). Ответ пользователя не компилируется заново — он просто
связывается с переменной, и интерпретация продолжается. Повторная компиляция нужна лишь
тогда, когда ответ меняет само намерение.

## Главный довод: язык программ — это API для 1С

Горизонт владельца — запросы из 1С по REST. Посмотрите, что происходит с интеграцией:

```
человек в чате 1С:   текст ──▶ компилятор (модель) ──▶ программа ──▶ интерпретатор
автоматизация 1С:    программа ─────────────────────────────────────▶ интерпретатор
```

**Внешней системе модель не нужна.** 1С (как и любой другой интегратор) отправляет
программы напрямую: детерминированно, без расхода токенов, с той же проверкой и тем же
журналом исполнения. Язык программ становится публичным контрактом сервиса, а чат —
лишь человеческим входом к нему. Ни одно другое предложение на собрании не даёт
интеграции такого уровня за сопоставимую цену.

## Слабые стороны (называю сам)

1. **Ставка на способность YandexGPT к компиляции не проверена.** Разведочный прототип
   S1 (см. `00-sobranie.md`) обязателен до выбора этой архитектуры: двадцать реальных
   формулировок, измерение доли валидных и семантически верных программ. Провал
   прототипа означает отклонение архитектуры; язык программ в этом случае остаётся
   только как API для машин.
2. **Планирование вслепую.** Программа строится до просмотра данных. Ветвление `if`
   по уже вычисленным переменным покрывает простые случаи; команда «исправь как обычно»
   требует контекста в сводке состояния (как и у всех); однако потоки, существенно
   зависящие от данных, упрутся в перекомпиляцию — а это возвращение модели в цикл,
   пусть редкое и ограниченное двумя попытками.
3. **Живость уступает акторной.** Перебивание исполняющейся программы и параллельные
   реплики — не моя стихия; операция `ask` — точка ожидания, а не ткань разговора.
   Для диалога как основного интерфейса это действительный недостаток, признаю.
4. **Проектирование языка — работа.** Удержать шесть операций под давлением «а давайте
   добавим циклы» — дисциплина того же рода, что проекции Летописца, только
   единовременная (при проектировании), а не ежедневная.

## Что стоит позаимствовать, даже если моё предложение отклонят

- **Программа как форма составной команды.** Даже в трамплине базовой линии
  маршрутизатор может вернуть вместо одной функции последовательность из двух-трёх
  вызовов: это дешевле по токенам и даёт предварительный просмотр плана.
- **Показ плана перед разрушающим действием** — лучшая из возможных форм подтверждения.
- **Язык программ как REST-контракт для 1С** — закладывать при любой архитектуре:
  синтетические команды `{fn, args}` из `fable-arch-x` суть вырожденная программа
  из одного вызова; расширение до последовательности ничего не ломает.
