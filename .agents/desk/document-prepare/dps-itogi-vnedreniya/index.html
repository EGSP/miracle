До DPS извлечение текста из файлов было разрозненным: синхронные HTTP-вызовы с mammoth и SheetJS, отдельные vision-джобы, разный формат выхода в FileContent. Document Prepare Service (DPS) ввёл единый асинхронный конвейер: файл на диске → durable job prepare-document → унифицированный markdown в PreparedDocument. Этот документ — итог внедрения для тех, кто подключает новые фичи или разбирает, почему что-то «не извлекается» как раньше.

0Зачем появился DPS

Проблемы старой модели

  • Синхронный extract в HTTP — таймауты на больших файлах
  • Разный выход: plain text, CSV-в-тексте, постраничный JSON
  • Vision и non-vision — разные пайплайны и точки входа
  • Потребители сами запускали извлечение (orders, UI)
  • FileContent без жёсткой связи с File

Цели DPS

  • Один выход: markdown в PreparedDocument
  • Durable jobs + восстановление после рестарта
  • Роутинг по домену файла (kreuzberg / LLM Vision)
  • Автоподготовка на upload; re-prepare по API
  • Потребители только читают, не запускают разметку
Ключевое правило после внедренияВся разметка файлов в markdown инициируется только DPS (хук FilesService.onFileSaved или явный POST /documents/:fileId/prepare). Домены orders, tc, scan не должны ставить prepare сами.

2Хронология фаз 1–7

  • Фаза 1 — инфраструктура
    Модуль document-prepare, Prisma PreparedDocument, kreuzberg в docker, одна job prepare-document.
  • Фаза 2 — Kreuzberg
    HTTP-адаптер, tool kreuzberg.extract.v1, KreuzbergConcurrencyLimiter, health-gating.
  • Фаза 3 — LLM Vision
    LlmVisionExtractor, tools render/recognize, промпты в vision/, ToolMemo для opId.
  • Фаза 4 — автоподготовка
    onFileSaved → fire-and-forget enqueuePrepare. Upload не падает при ошибке enqueue.
  • Фаза 5 — readers
    ApplicationChunkReader на Effect/Stream; analyse-application без extract-visual.
  • Фаза 6 — deprecation
    Sync extract → 410; legacy endpoint как мост для старых клиентов.
  • Фаза 7 — dependency audit
    Удалены mammoth, papaparse, xlsx из back-nest; exceljs сохранён для отчётов orders.

3Поток для оператора и API

Жизненный цикл файла

  1. Загрузка: POST /files/upload или файл заявки заказа (POST /orders/:id/applications/file).
  2. Запись File в БД → notifyFileSaved.
  3. DPS (если формат поддерживается) ставит job prepare-document, статус queued.
  4. Ожидание: running → succeeded или failed.
  5. Проверка: GET /documents/:fileId/prepared.
  6. Повтор: POST /documents/:fileId/prepare.
EndpointНазначениеСтатус
GET /documents/:fileId/preparedСтатус и markdownАктуальный
POST /documents/:fileId/prepareRe-prepareАктуальный
POST /files-content/:fileId/extractСинхронное извлечение410 Gone
GET /files-content/:fileIdИстория FileContentRead-only
Front ещё не мигрированFileCard и useExtractFileContent вызывают старый extract → пользователь получит 410. Целевое: статус PreparedDocument и кнопка re-prepare через DPS API.

5Анализ заявок и контракты

Джоба analyse-application не готовит файлы. Она вызывает ApplicationChunkReader.read(application), который для file-applications требует PreparedDocument.status === 'succeeded'.

Статус PreparedDocumentПоведение reader
нет записиОшибка: нет подготовленного документа
queued / runningОшибка: ожидает / подготавливается
failedОшибка с текстом из prepared.error
succeededОдин чанк { chunkKey: 'markdown', chunk: { text } }
Планируемый контракт на уровне заказаАнализ заказа возможен, когда все file-applications имеют готовый PreparedDocument. Сейчас проверка fail-fast внутри reader по каждому файлу; явный gate на уровне оркестратора заказа — кандидат на улучшение.

API reader (только Effect):

read(application): Effect<ReadChunk[], ApplicationReadError>
getMarkdown(fileId): Stream<string, ApplicationReadError>  // сейчас одна итерация

7Дублирующаяся логика

7.1 Два vision-пайплайна

DPS

LlmVisionExtractor + JobTools
vision/prompts.ts, render-pages.ts
Результат → PreparedDocument

Legacy scan

scan.shared.ts → visionRecognize
Child jobs, submitOnceEffect
Результат → FileContent

Промпты LLM_VISION_* re-export в scan для старых jobs; изменения scale/usedPages/poll нужно помнить в двух ветках, пока scan не выведен.

7.2 Poll Yandex

Inline-цикл в LlmVisionExtractor.extract() и в VisionRecognizeTool — намеренное дублирование (KISS). При смене интервала или условия done править два места.

7.3 Загрузка файла в DPS tools

files.effects.get(fileId) → mapError → fail if null → getFilePath

Повторяется в kreuzberg-extract.tool.ts и vision-render.tool.ts. Кандидат: files.effects.require(fileId).

7.4 DocumentExtractor vs tools

  • Kreuzberg: tool вызывает extractor.extract() целиком.
  • Vision: tool — гранулярно (renderPages, submit, pollOnce); extract() дублирует цикл для порта.

9Что упростить (приоритеты)

Высокий

  1. Мигрировать front на PreparedDocument (статус, re-prepare).
  2. files.effects.require(fileId) — убрать boilerplate в DPS tools.
  3. Единый getPreparedMarkdown(fileId) в DocumentPrepareService (логика статусов сейчас в ApplicationChunkReader).

Средний

  1. tc-extract.job → PreparedDocument.
  2. Deprecate scan vision jobs или перевести на DPS.
  3. Gate «все application prepared» перед batch analyse-order.

Низкий

  1. Таблица engine → steps[] в prepare-document.job.
  2. Удалить POST extract после миграции клиентов.
  3. Убрать extract-visual.job из registry.

11Чеклист для нового кода

  • Новый потребитель текста файла → PreparedDocument, не FileContent
  • Не вызывать enqueuePrepare из доменов-потребителей — только хук или POST API
  • Создание File в транзакции → files.create(..., { tx }) + notifyFileSaved после commit
  • Шаги prepare — JobTool + ToolMemo, не child JobRun
  • Vision-промпты — из document-prepare/vision/prompts.ts
  • Документация на русском: README модуля + dp.report.md
