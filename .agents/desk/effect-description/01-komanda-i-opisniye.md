# Глава 1. Команда и описание

## Команда, исполняемая на месте

Возьмём строку, которую каждый из нас писал тысячу раз:

```ts
const user = getUser(id);
sendWelcomeEmail(user);
```

Прочитайте её так, как читает машина. Управление доходит до первой строки, и тут же делается работа: код идёт в базу, ждёт ответа, кладёт результат в переменную. Только после того, как поход состоялся, управление переходит ко второй строке. Вызов и исполнение слиты в одну точку времени. Назвать функцию здесь означает её выполнить.

Это повелительное наклонение. Каждая строка — приказ исполнителю, а программа целиком — последовательность приказов, которые отрабатывают по мере того, как до них доходит очередь. Чтобы понять фрагмент кода, мы мысленно его проигрываем: встаём на место машины и шаг за шагом исполняем строки в голове. Смысл фрагмента совпадает с тем, что случится во время его выполнения.

У такого чтения есть скрытая цена. Смысл строки не записан в ней самой, он размазан по всей цепочке исполнения. Чтобы узнать, что будет при ошибке внутри `getUser`, надо знать, кто выше по стеку ловит исключения. Чтобы понять, сколько раз код сходит в базу, надо проследить весь путь управления. Текст показывает шаги, а поведение приходится восстанавливать.

## Вызов, который возвращает описание

Теперь представим, что вызов функции ничего не выполняет. Он возвращает значение, которое описывает будущую работу. Сравним две подписи одной и той же функции:

```ts
// Вызов и исполнение слиты: к следующей строке поход в базу уже идёт.
function getUser(id: string): Promise<User> { /* ... */ }

// Вызов возвращает описание: пока его не запустят, в базу никто не пошёл.
function getUser(id: string): Effect<User, DbError> { /* ... */ }
```

Во второй версии выражение `getUser(id)` не ходит никуда. Оно строит и отдаёт значение, которое читается так: «когда меня запустят, я схожу за пользователем; если не дойду — это будет `DbError`». Перед нами чертёж работы, а не сама работа. Постройка по чертежу откладывается до самого края программы, где описание передают исполнителю; в Effect это отдельный вызов вроде `runPromise` или `runFork`. До этого края мы только пишем чертежи и складываем их друг с другом.

Слово «чертёж» здесь не для красоты, оно точно указывает на то, что значение и его исполнение разнесены во времени. У промиса этого разнесения нет: промис начинает работу с момента создания. Описание холодное — оно лежит и ждёт, пока его не возьмут в работу, и до этого момента его можно изучать, передавать и менять.

## Что даёт разнесение

Как только работа стала значением, с ней можно обращаться как с любыми данными. Это открывает четыре простые возможности, и из них вырастает почти всё дальнейшее.

Описание можно **назвать**. Переменная или функция, в которой лежит чертёж, начинает говорить о том, что этот чертёж означает.

```ts
// Не «сходи в базу», а «требуемый для заказа пользователь».
const requiredUser = requireUser(order.userId);
```

Описание можно **отложить и переиспользовать**. Один и тот же чертёж применяют в разных сценариях, потому что сам по себе он ещё ничего не сделал.

```ts
const loadConfig = readJsonFile(configPath); // описание чтения, а не чтение
// дальше loadConfig пригодится и при старте, и при горячей перезагрузке
```

Описание можно **обернуть** — взять чужой чертёж и построить вокруг него свой, побогаче. Так `require` вырастает над `get`, и к этому мы вернёмся отдельной главой.

Описание можно **скомпоновать** — соединить несколько чертежей в один, и соединение читается как фраза:

```ts
const program = pipe(
  requireUser(id),
  flatMap((user) => requireActiveSubscription(user)),
  flatMap((sub) => chargeMonthlyFee(sub)),
);
```

Здесь не выполнено ни одной операции. Здесь стоит составное описание: «взять требуемого пользователя, затем его действующую подписку, затем списать абонентскую плату». Поведение записано прямо в тексте, и чтобы его понять, не нужно проигрывать программу в голове, достаточно прочитать предложение.

## Сдвиг наклонения

Разница между двумя подходами — это разница между повелительным и изъявительным наклонением. В повелительном мы командуем исполнителю по шагам, и программа есть то, что происходит. В изъявительном мы описываем, какой хотим видеть программу, и программа есть то, что записано. Действия никуда не исчезают, поход в базу всё равно случится, но он отступает под управление исполнителя, а в текст, который мы пишем и читаем, поднимается намерение.

Такой сдвиг меняет и способ чтения. Раньше мы читали программу как сценарий исполнения. Теперь мы читаем её как высказывание о том, что должно получиться. А раз код стал высказыванием, дальше встаёт вопрос о словах, которыми оно сделано. И первое слово в любом высказывании о работе — это название самой работы. Но прежде чем говорить о названиях, посмотрим на форму, которую принимает целая процедура, когда поток управления тоже становится значением.
