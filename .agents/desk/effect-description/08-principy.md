# Глава 8. Принципы

Соберём исследование в набор правил. Это не свод на все случаи, а линза, через которую стоит смотреть на проектирование. Каждый принцип вырос из предыдущих глав, и рядом с ним указано, откуда он. Применять их нужно с поправкой на цену, о которой шла речь в шестой главе: описание окупается дисциплиной, и без неё превращается в красивую форму.

## 1. Описывай намерение, исполнение откладывай на край

Функция пусть возвращает значение, описывающее работу, а не выполняет работу на месте вызова. Тогда это значение можно назвать, отложить, обернуть и скомпоновать. Исполнение собери в одной явной точке на краю программы.

```ts
const program = pipe(requireUser(id), flatMap(chargeMonthlyFee));
// работа начнётся только здесь:
Effect.runPromise(program);
```

*Из глав 1 и 6.*

## 2. Делай поток управления значением

Последовательность, ветвление, цикл, повтор, тайм-аут, параллелизм выражай комбинаторами, а не вшивай в тело синтаксисом. Тогда «что мы делаем» отделяется от «как именно это идёт», и второе настраивается снаружи, не задевая первое.

```ts
// «Сколько разом» и «сколько попыток» — снаружи, тело не тронуто.
pipe(Effect.forEach(pages, extractPage, { concurrency: 4 }), Effect.retry(networkRetry));
```

*Из главы 2.*

## 3. Называй по потребности вызывающего, механику прячь вниз

Слово наверху пусть говорит о намерении того, кто вызывает, а не о приёме исполнения. Глаголы механики оставь нижнему слою адаптеров. Чем выше слой, тем больше слово о намерении.

```ts
runExtract: (filePath: string) => Effect<PreparedResult, ExtractError>   // механика, низ
prepareDocument: (fileId: string) => Effect<PreparedResult, ExtractError> // намерение, верх
```

*Из главы 3.*

## 4. Заводи слово только под решение предметной области

Отдельное название оправдано, когда за ним стоит повторяющееся и важное решение задачи. Если всё, что добавляет слово, — это завёрнутая проверка, выражай её общим комбинатором, а не семейством одноимённых методов. Так словарь остаётся языком и не вырождается в частный диалект.

```ts
// Вместо requireUser, requireOrder, requireInvoice — одна операция:
const file = pipe(get(id), orFail(() => new FileNotFoundError({ id })));
```

*Из главы 4.*

## 5. Поднимай существенное в подпись

Исход, возможные сбои и зависимости пусть стоят в типе. Тогда контракт читается до запуска, а перечни сбоев складываются сами при компоновке, и нигде не теряются.

```ts
loadUser: (id: string) => Effect<User, UserNotFound | DbError, Database>;
//                                 ^исход  ^сбои               ^зависимость
```

*Из главы 5.*

## 6. Держи тип честным

Подпись — это контракт, и он полезен ровно настолько, насколько правдив. `never` должен означать, что наружу сбоя нет; перечень сбоев не должен врать. Лгущий тип хуже отсутствующего, потому что ему доверяют, а для машинного читателя он опаснее вдвойне.

```ts
// Обещание `never` сдержано: любой исход обработчика остаётся внутри.
const guarded = (item: Item) =>
  handle(item).pipe(Effect.catchAllCause((cause) => report(cause)));
```

*Из глав 5 и 7.*

## 7. Не выпускай необработанную развилку наружу

Молчаливый `null` в возвращаемом типе — это развилка, которую кто-то обязан не забыть закрыть. Где можно, выражай отсутствие явной формой, которую нельзя случайно пронести дальше, и не выпускай сырую пустоту из реализации, если потребность вызывающего — получить значение.

```ts
findFile:    (id: string) => Effect<Option<File>, DbError>;          // отсутствие видно
requireFile: (id: string) => Effect<File, FileNotFoundError | DbError>; // отсутствие закрыто
```

*Из главы 4.*

## 8. Имей одну явную границу исполнения

Где-то описание становится работой. Пусть эта граница будет явной и по возможности единственной, а не размазанной по коду. Тогда видно, где программа запускается, и легче рассуждать об отмене, сбоях рантайма и параллелизме.

*Из главы 6.*

## 9. Сдерживай словарь

Возможность называть и надстраивать соблазнительна. Заводи слова и слои там, где они несут смысл, и оставляй прямую механику там, где слой был бы церемонией. Разросшийся словарь читается хуже честной прямой записи.

*Из главы 6.*

## 10. Пиши так, будто читатель не может запустить программу

Это принцип, который собирает остальные. Поднимай смысл в названия и типы, держи его рядом с местом чтения, говори правду в подписи. Такому читателю — и человеку, рассуждающему чтением, и языковой модели, рассуждающей по тексту, — доступно только то, что записано. Чем больше существенного записано, тем меньше приходится угадывать.

*Из глав 6 и 7.*

## Как этим пользоваться

Принципы тянут в одну сторону: переносить смысл из поведения во время исполнения в текст и типы. Они не отменяют здравого смысла и цены, которую мы назвали. Описание окупается, когда слова стоят за решениями задачи, словарь сдержан, а типы говорят правду. При этих условиях программа начинает говорить, что она означает, и это служит каждому, кто её читает, кем бы он ни был.
