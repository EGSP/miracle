# Глава 2. Процедуры как данные

В прошлой главе значением стал один вызов. Теперь посмотрим, что происходит с целой процедурой, когда значением становится и она.

## Процедура как последовательность приказов

В повелительном коде процедура — это набор операторов, которые исполняются ради их действия. Ветвление, цикл, обработка ошибок собраны из синтаксиса языка: `if`, `for`, `try`. Этот синтаксис вшит в тело процедуры намертво. Возьмём типичную задачу: загрузить страницы документа, для каждой получить разметку, собрать результат.

```ts
async function prepare(doc: Document): Promise<string> {
  const parts: string[] = [];
  for (const page of doc.pages) {
    const text = await extractPage(page); // одна страница за другой
    parts.push(text);
  }
  return parts.join("\n");
}
```

Поток управления здесь — это форма записи. Цикл `for` нельзя взять в руки и передать дальше, нельзя отделить «как мы обходим страницы» от «что делаем с каждой». Если завтра понадобится обрабатывать страницы по четыре параллельно, придётся переписать тело: завести семафор, насобирать промисы, аккуратно их свести. Если понадобится повторять неудачную страницу трижды — снова правка тела, теперь вокруг `extractPage` появится цикл попыток. Каждое новое требование к тому, *как* идёт работа, заставляет менять код, который описывает, *что* это за работа.

## Поток управления, ставший значением

Когда вызов стал описанием, описанием становится и способ соединять вызовы. Последовательность, ветвление, цикл, обработка ошибок, повторы, параллелизм — всё это превращается в комбинаторы, и каждый комбинатор сам по себе значение. Та же процедура на описаниях выглядит так:

```ts
const prepare = (doc: Document): Effect<string, ExtractError> =>
  pipe(
    Effect.forEach(doc.pages, (page) => extractPage(page)), // обход страниц как значение
    Effect.map((parts) => parts.join("\n")),
  );
```

`Effect.forEach` — это цикл, но не синтаксис, а значение-комбинатор. Он описывает обход, не выполняя его. И раз обход стал значением, его поведением можно управлять снаружи, не трогая тело. Захотели параллелизм — добавили параметр, тело осталось прежним:

```ts
const prepare = (doc: Document): Effect<string, ExtractError> =>
  pipe(
    Effect.forEach(doc.pages, (page) => extractPage(page), { concurrency: 4 }),
    Effect.map((parts) => parts.join("\n")),
  );
```

Разница в одном поле настроек, а не в переписанном цикле. «Что мы делаем со страницей» и «сколько страниц идёт одновременно» разъехались на две независимые вещи, и вторую можно менять, не задевая первую.

## Целую процедуру можно обернуть

Главное следствие в том, что описанную процедуру можно украшать снаружи, надстраивая над ней поведение. Повтор при неудаче — это не цикл внутри тела, а обёртка вокруг готового описания:

```ts
const robustPrepare = (doc: Document): Effect<string, ExtractError> =>
  pipe(
    prepare(doc),
    Effect.retry(Schedule.recurs(3)), // повторить до трёх раз
    Effect.timeout("30 seconds"),     // и не дольше тридцати секунд
  );
```

`prepare` ничего не знает о повторах и тайм-ауте. Политику повтора и предел времени мы добавили поверх, как добавляют слой. Сам `Schedule.recurs(3)` — тоже значение: расписание попыток, которое можно вынести, назвать и переиспользовать на других процедурах.

```ts
// Политика повтора как именованное значение предметной области.
const networkRetry = Schedule.recurs(3).pipe(Schedule.addDelay(() => "200 millis"));

const a = pipe(loadCatalog, Effect.retry(networkRetry));
const b = pipe(loadProfile, Effect.retry(networkRetry));
```

То же касается обработки ошибок. В повелительном коде `try/catch` оборачивает блок и существует только на месте. В описательном обработка ошибки — это комбинатор над значением, и его видно в выражении:

```ts
const safe = pipe(
  requireFile(id),
  Effect.catchTag("FileNotFoundError", () => useFallbackTemplate()),
);
```

## Поведение, которое раньше пришлось бы программировать

Этот сдвиг хорошо виден на конкуренции за ресурс. В рабочем коде у нас есть линия обработки: очередь с ограниченной длиной и несколько одинаковых рабочих, которые её разбирают. Рабочий — это описание бесконечного цикла:

```ts
// Рабочий: взять элемент, обработать, повторять вечно. Целиком — значение.
const loop = Queue.take(queue).pipe(Effect.flatMap(handle), Effect.forever);
```

А обратное давление — свойство очереди, а не код, который мы писали руками. Когда очередь заполнена, `offer` не падает и не крутит процессор, он засыпает, пока место не освободится:

```ts
// Если очередь полна, этот шаг сам приостановится до свободного места.
yield* Queue.offer(queue, item);
```

В повелительном мире и цикл рабочего, и пробуждение по освобождению места пришлось бы собирать вручную: условные переменные, проверки, аккуратная синхронизация. Здесь конкуренция и обратное давление заданы как свойства значений, которые мы соединили. Мы их описали, а не запрограммировали по шагам.

## Что это меняет в форме кода

Когда поток управления стал значением, процедура перестаёт быть телом из операторов и становится выражением из описаний. Из этого следует несколько вещей сразу.

Сцепление, ветвление, цикл, повтор, тайм-аут, параллелизм — всё это теперь отдельные, переносимые куски, которые можно вынести, назвать и применить в другом месте. «Что делаем» отделяется от «как именно это идёт», и второе настраивается снаружи, не задевая первое. А целая процедура получает ровно тот же статус, что был у одного вызова: у неё есть значение, у неё есть подпись, и её можно вставить в большее выражение как одно слово.

И вот тут возвращается вопрос, отложенный в конце прошлой главы. Если и отдельная операция, и целая процедура стали значениями, которым мы даём названия, то названия начинают нести главный груз смысла. С них и продолжим.
