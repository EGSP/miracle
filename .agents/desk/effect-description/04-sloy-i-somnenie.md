# Глава 4. Слой над механикой и сомнение в нём

## Как это задумано

Изложим приём так, как он выглядит в защиту. Есть механика доступа к хранилищу. Запись там может быть, а может не быть, и честный тип это признаёт:

```ts
get: (id: string) => Effect<File | null, DbError>;
```

`get` ничего не решает за вызывающего. Он сообщает положение дел: вот файл, либо вот пустота, разбирайся по своей ситуации. И ситуации правда разные. Фоновому уборщику кэша пустота — норма: записи нет, и хорошо, идём дальше. Обработчику, который готовит документ, пустота — катастрофа: без файла его работа бессмысленна.

`require` обслуживает вторую ситуацию и надстраивается над первой:

```ts
const require = (id: string): Effect<File, FileNotFoundError | DbError> =>
  pipe(
    get(id),
    flatMap((file) =>
      file ? Effect.succeed(file) : Effect.fail(new FileNotFoundError({ id })),
    ),
  );
```

`get` остаётся как был, это фундамент, механика. Поверх него `require` кладёт слой смысла: решение о том, что отсутствие файла недопустимо, и слово для этого отсутствия. Две функции обслуживают две разные потребности, и каждая говорит ровно то, что нужно своему вызывающему. Звучит стройно. Теперь по очереди усомнимся.

## Первое сомнение: две двери в одну комнату

Мы оставили в публичном интерфейсе две функции, ведущие к одному хранилищу. Каждый вызывающий теперь обязан выбрать правильную дверь. Ничто не мешает ему ошибиться — взять `get` там, где по смыслу нужен `require`, получить обратно `File | null` и снова, руками, написать проверку на пустоту.

```ts
// Взяли не ту дверь — и проверка вернулась на место вызова.
const file = yield* get(id);
if (!file) throw new Error("not found");
```

Та самая россыпь проверок, которую мы собирали в одно место, возвращается, просто теперь у неё есть удобный повод появиться. Получается, мы не столько устранили дублирование, сколько добавили способ его избежать, оставив рядом способ не избежать. Дисциплина переехала из «не забудь проверить пустоту» в «не забудь выбрать `require` вместо `get`». Стало ли надёжнее — вопрос открытый, и ответ зависит от того, насколько легко в коде случайно дотянуться до `get`.

## Второе сомнение: это слово или спрятанный `if`

Спросим прямо: `require` — это новое слово предметного языка или просто `get` с приклеенным охранником? Если завтра понадобятся `requireUser`, `requireOrder`, `requireInvoice`, `requireSeat`, мы рискуем построить не словарь, а частный диалект, где на каждую сущность заведено по глаголу-близнецу. Такой диалект, кроме его авторов, никто не читает свободно, и каждое новое слово в нём — копия одной и той же проверки под новым названием.

Возможно, честнее не плодить методы, а признать, что за всеми ними стоит одна операция: «возьми описание, которое может дать пустоту, и преврати пустоту в осмысленный сбой». Её можно выразить одним общим комбинатором:

```ts
// Одна операция вместо семейства одноимённых методов.
const orFail =
  <A, E2>(onAbsent: () => E2) =>
  <E>(self: Effect<A | null, E>): Effect<A, E | E2> =>
    flatMap(self, (a) => (a == null ? Effect.fail(onAbsent()) : Effect.succeed(a)));

// На месте вызова сбой назван прямо там, где о нём решают:
const file = pipe(get(id), orFail(() => new FileNotFoundError({ id })));
```

Здесь нет ни `requireFile`, ни его будущих братьев. Есть один приём, применённый к механике в точке вызова, и словарь не разрастается. Граница пользы, похоже, проходит так: метод вроде `requireFile` оправдан, когда за словом стоит решение предметной области, повторяющееся и важное настолько, что заслуживает собственного слова. Если же всё, что добавляет слово, — это завёрнутая проверка на пустоту, общий комбинатор честнее.

## Третье сомнение: а может, не прав сам фундамент

До сих пор мы принимали `get` с его `File | null` как данность и спорили лишь о надстройке. Стоит усомниться и в основании. Откуда вообще взялась пустота в типе `get`? Мы объявили её честностью: хранилище может не содержать записи, и тип это признаёт. Но `null` в возвращаемом типе — это и есть та необработанная развилка, которую кто-то обязан не забыть закрыть. Мы потратили `require`, чтобы её закрывать. Может быть, дело не в том, что над `get` нужна надстройка, а в том, что `get` в нынешнем виде вообще не стоило выпускать наружу.

Тогда возможен другой ход. Сделать единственной публичной операцией ту, что выражает потребность, а механику с пустотой спрятать в реализацию:

```ts
// Наружу — только намерение. Пустота не доезжает до вызывающего.
requireFile: (id: string) => Effect<File, FileNotFoundError | DbError>;

// А «есть или нет» выражаем не пустотой, а явной, читаемой формой:
findFile: (id: string) => Effect<Option<File>, DbError>;
```

`Option<File>` вместо `File | null` — это не косметика. `null` легко не заметить и пронести дальше по коду; `Option` нельзя случайно использовать как файл, его приходится сознательно раскрыть, и развилка «есть/нет» становится видимой операцией, а не молчаливой возможностью. У нас всё ещё две функции, но обе выражают намерение: одна — «файл обязателен», другая — «файл под вопросом, и я готов это обработать». Слово-действие `get`, отдающее `null`, в такой картине исчезает, и вместе с ним исчезает дверь, в которую можно войти по ошибке.

Я не утверждаю, что этот ход правильный во всех случаях. У него своя цена: `Option` — лишняя обёртка, которую кто-то должен раскрывать, и в маленьком модуле она может оказаться церемонией ради чистоты. Я показываю, что исходная картинка «`get` остаётся, поверх него растёт `require`» не единственная и, возможно, не лучшая. Сомнение направлено и на того, кто ставил задачу: установка «надстраиваем смысл над механикой» удобна, но она молча узаконивает существование механики с дырой в типе. Иногда правильный ответ — закрыть дыру в самом основании.

## Что отсюда забрать

Приём «механика внизу, намерение сверху» работает, но при условиях. Слово-намерение несёт смысл тогда, когда за ним стоит решение предметной области, а не просто спрятанная проверка. Семейство одноимённых надстроек стоит остановить и заменить общим комбинатором, как только выясняется, что все они добавляют одно и то же. А прежде чем надстраивать слой над механикой, которая возвращает пустоту, полезно спросить, должна ли эта пустота вообще покидать реализацию.

Во всех трёх сомнениях есть общая нить. Спор идёт не столько о словах, сколько о том, что функция обещает вызывающему и что она признаёт возможным. А обещание и набор возможностей записаны не только в названии, они записаны в типе. Поэтому дальше посмотрим, как подпись достраивает название до полного высказывания.
