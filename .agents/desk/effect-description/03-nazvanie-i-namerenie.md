# Глава 3. Название как место намерения

Под «названием» здесь и дальше понимается идентификатор функции, метода или значения — то слово, которым мы их называем в коде. Из таких слов складывается словарь, на котором мы говорим о программе, и эта глава о том, что мы этими словами говорим.

## О чём говорит название в повелительном коде

Посмотрите на привычные названия функций: `getUser`, `fetchOrders`, `loadConfig`, `saveDocument`, `computeTotal`. Почти все они — глаголы действия, и каждый сообщает, что исполнитель делает в момент вызова. Это естественно: раз вызов есть исполнение, название называет исполняемое действие. Оно отвечает на вопрос «что произойдёт, когда я тебя позову».

Такие слова говорят о механике. `fetchOrders` сообщает про сетевой запрос, `loadConfig` — про чтение с диска, `computeTotal` — про вычисление. Тот, кто читает название, узнаёт способ, которым работа будет сделана. Часто это знание ему ни к чему: тому, кто складывает приветственное письмо, безразлично, добыт ли пользователь сетевым запросом, из кэша или из тестовой заглушки. Ему нужен пользователь.

## О чём может говорить название, когда вызов описывает

Когда вызов превратился в описание, у названия высвобождается работа. Ему больше не обязательно рассказывать про механику исполнения, этим занят чертёж внутри. Название может говорить о другом: о том, что этот кусок работы значит для того, кто его вызывает. О намерении, а не о приёме.

Вернёмся к паре, с которой всё началось. В файловом сервисе есть два соседа:

```ts
get:     (id: string) => Effect<File | null, DbError>
require: (id: string) => Effect<File, FileNotFoundError | DbError>
```

`get` назван по действию: «достань, что есть; может, ничего и нет». Это честное слово для механики, оно описывает доступ к хранилищу, где запись может отсутствовать. `require` назван по намерению вызывающего кода: «мне нужен этот файл». В нём нет ни слова о том, как файл достаётся. Зато в нём есть утверждение о мире, важное вызывающему: файл обязан существовать, а его отсутствие — это осмысленное событие с названием `FileNotFoundError`.

Тот, кто вызывает `require`, не интересуется механикой доступа. У него есть потребность — файл, без которого дальше нельзя. `require` эту потребность и выражает. Он берёт механику `get` и надстраивает над ней смысл: что значит отсутствие, как его называть, можно ли продолжать без файла. Раньше это знание жило бы в голове разработчика и в россыпи проверок у каждого вызывающего:

```ts
// Знание «без файла нельзя» размазано по местам вызова.
const file = await db.files.findUnique({ where: { id } });
if (!file) throw new Error("not found");
```

Теперь оно собрано в одном слове, и место вызова говорит о потребности, а не о проверке:

```ts
// «Возьми требуемый файл» — решение об отсутствии уже внутри слова.
const file = yield* requireFile(id);
```

## Название и намерение читаются как фраза

Сила описательного слова видна, когда из таких слов складывают программу. Сравните, как читаются две версии одного намерения.

```ts
// Слова-действия: читатель восстанавливает смысл из механики.
const file = await db.files.findUnique({ where: { id } });
if (!file) throw new Error("not found");
const text = await extractText(file);
```

```ts
// Слова-намерения: смысл записан прямо в выражении.
const program = pipe(
  requireFile(id),
  flatMap((file) => extractMarkdown(file)),
);
```

Второе выражение читается как предложение на языке предметной области: «возьми требуемый файл, затем извлеки из него разметку». Проверка на отсутствие не пропала, она ушла внутрь слова `requireFile` и стала частью его значения. Читателю не нужно держать её в голове, за неё отвечает название.

Когда таких слов набирается много, они образуют словарь, на котором можно говорить о системе: `requireFile`, `reserveSeat`, `chargeMonthlyFee`, `publishDraft`. Это те же слова, которыми о системе говорят вслух, без кода. Когда язык кода совпадает с языком разговора, обсуждение задачи с коллегой идёт теми же словами, что стоят в исходниках, и перевод между «как мы это называем» и «как это записано» больше не нужен.

## Как выбирать название в описательном коде

Из сказанного складывается несколько ориентиров. Это направление мысли, а не свод правил.

**Называйте по потребности вызывающего, а не по приёму исполнения.** Спросите: что нужно тому, кто меня позовёт, и что он будет считать нормой, а что сбоем. `requireFile` отвечает на этот вопрос лучше, чем `getFileOrThrow`: первое слово говорит о потребности, второе всё ещё описывает механику с приклеенным поведением.

**Пусть слово называет результат как намерение, а механику прячет.** `activeSubscription` лучше, чем `queryActiveSubscriptionFromBilling`. Откуда взялась подписка — дело реализации, и оно может смениться, не задев ни одного вызывающего.

**Оставляйте слова-действия нижнему слою.** Глаголы механики уместны там, где мы и правда описываем приём: у адаптера к базе, у HTTP-клиента, у функции записи на диск.

```ts
// Нижний слой: честный глагол механики.
runExtract: (filePath: string) => Effect<PreparedResult, ExtractError>

// Слой выше: слово предметной области, механика спрятана.
prepareDocument: (fileId: string) => Effect<PreparedResult, ExtractError>
```

Чем ниже слой, тем больше слово говорит о механике; чем выше, тем больше о намерении.

**Дайте названию и подписи звучать вместе.** Слово — половина высказывания, вторую половину несёт тип. `require(id): Effect<File, FileNotFoundError>` целиком читается как фраза: «требуемый файл по идентификатору, который может не найтись». Этой связке посвящена отдельная глава, потому что подпись в описательном коде работает наравне с названием.

## Куда это ведёт

Получается стройная картина. Механика прячется в нижнем слое под словами-действиями, наверху мы говорим словами-намерениями и складываем из них фразы. `require` стоит над `get` и добавляет к нему смысл; вызывающий код читает потребности, а не приёмы.

Картина стройная, и поэтому к ней стоит присмотреться подозрительно. Мы только что оставили в системе две функции вместо одной и записали это в достоинства. Мы предположили, что новое слово несёт новый смысл, хотя внутри оно может оказаться старой функцией с приклеенной проверкой. Прежде чем строить на этом приёме, разберёмся, всегда ли он работает так хорошо, как сейчас прозвучало.
