# Диалоговый оркестратор: варианты архитектуры (Board / Turn / FunctionRouterTool)

> Статус: проектирование, 19.07.2026. Документ обобщает обсуждение перехода сервиса
> в диалоговый режим работы.
>
> Решения, принятые ранее и в настоящем документе не пересматриваемые:
> библиотека LangGraph не используется; наблюдаемость (Langfuse) подключается через
> существующий порт `LlmUsageSink` независимо от устройства оркестратора; маршрутизация
> выполняется одиночным обращением к модели с обязательным выбором функции
> (`tool_choice: required`) — модель принимает ровно одно решение за одно обращение;
> модели передаётся сводка текущего состояния, а не история переписки.

---

## 1. Цель и основные понятия

Сервис должен стать диалоговым: пользователь отдаёт команды и сообщает сведения,
необходимые для составления заказа, а языковая модель определяет, какую функцию системы
следует вызвать (полный анализ, частичный анализ, правка позиций, простой ответ).
При этом модель не управляет процессом в целом: каждая функция сама определяет
свой следующий шаг. Таким образом, свобода модели ограничена входом — пониманием
команды, — а исполнение остаётся детерминированным.

### Словарь терминов

Проектные термины (используются во всём документе):

| Термин | Значение |
|---|---|
| **Доска (Board)** | Разговор с пользователем вместе с его текущим контекстом: сводкой заказа, упомянутыми объектами, ожидающими подтверждениями. Хранится как данные, а не как объект в памяти процесса. |
| **Ход (Turn)** | Единица действия пользователя или системы, включая промежуточные сообщения о состоянии («извлекаю позиции…»). |
| **Маршрутизатор (FunctionRouterTool)** | Обращение к модели, в котором она выбирает одну функцию и её аргументы. Может вызываться несколько раз за один ход. |
| **Определение функции (FunctionDefinition)** | Описание одной возможности системы: имя, описание, схема аргументов, тело. По форме совпадает с существующим `JobTool`. |
| **Джоба (Job)** | Единица работы существующего фреймворка задач с деревом запусков (`JobRun`), устойчивая к перезапуску процесса. |
| **Устойчивость (durable)** | Свойство вычисления переживать перезапуск сервера: состояние сохраняется в БД, и после рестарта работа продолжается с последней контрольной точки, а не начинается заново. |
| **Однократная отправка (submit-once)** | Приём из существующего кода: идентификатор дорогой операции записывается в память инструмента до начала ожидания, поэтому при перезапуске операция не отправляется повторно. |
| **Трамплин** | Плоский цикл-диспетчер: функция не вызывает маршрутизатор сама, а возвращает результат-сигнал, и решение о продолжении принимает внешний цикл. Так исключается неявная рекурсия. |

Владелец сформулировал требования к архитектуре: она должна легко пониматься,
состоять из плоских слоёв и не содержать глубоко вложенных зависимостей. Поэтому все
варианты ниже собраны из четырёх слоёв, каждый из которых знает о нижележащем только
его публичный контракт:

```
Лента записей (данные)
   → Цикл хода (единственная точка управления)
      → Маршрутизатор (одно решение модели)
         → Реестр функций (плоский список возможностей)
```

Функции не имеют доступа к доске целиком — только к узкому контексту `FunctionContext`.
Маршрутизатор никогда не вызывается изнутри функций — исключительно из цикла хода,
по принципу трамплина.

## 2. Инварианты, общие для всех вариантов

Перечисленные правила не зависят от выбора варианта: они следуют из ранее принятых
решений и из зафиксированных уроков проекта (`dps-audit.md`, `order/README.md`,
`08-principy.md`).

1. **Сводка вместо переписки.** Маршрутизатору передаётся компактное типизированное
   состояние `DialogState`: проекция позиций и типов продукции, последний упомянутый
   объект (чтобы разрешать местоимения вида «у неё»), ожидающие подтверждения.
   История сообщений в модель не подаётся.
2. **Одно решение модели за одно обращение.** Циклом управляет код. Результат
   `Continue` означает продолжение внутри того же хода (разбор составной команды);
   результаты `Reply` и `AwaitUser` завершают ход.
3. **Решение маршрутизатора сохраняется до исполнения функции.** Модель
   недетерминирована, поэтому при возобновлении после перезапуска сохранённое решение
   берётся из памяти, а не запрашивается заново — иначе продолжение хода разойдётся
   с уже выполненными шагами.
4. **Память хода компактна.** В журнал шагов записываются решения и краткие результаты;
   объёмные данные (размеченный текст, изображения) хранятся отдельно и упоминаются
   по идентификатору. Урок проекта: хранение base64-содержимого в `job_runs.memo`
   недопустимо раздувает строки БД.
5. **Разрушающие действия — только через подтверждение.** Повторный анализ уничтожает
   существующие позиции, поэтому функция с разрушающим исходом возвращает `AwaitUser`
   и записывает ожидающее подтверждение в состояние доски; исполнение происходит лишь
   после явного согласия пользователя в следующем ходе. Это диалоговый аналог
   действующего правила «разрушающие операции живут на слое запуска, тело джобы
   безопасно к повтору».
6. **Долг в транспорте.** Файл `yandex-openai.transport.ts` в настоящий момент
   разбирает только текстовые элементы ответа (`message` / `output_text`). Для вызова
   функций требуется передавать поля `tools` и `tool_choice` в параметры запроса и
   разбирать элементы вида `function_call` из массива `response.output` (поле
   `arguments` приходит строкой: её нужно разобрать как JSON и проверить схемой Zod).
7. **Каждое решение маршрутизатора записывается** (Langfuse и учётная книга токенов) —
   это обеспечивает воспроизводимость и разбор инцидентов при недетерминированном входе.

Общие типы, одинаковые во всех вариантах:

```ts
type TurnResult =
  | { _tag: 'Reply';     message: string }        // ход завершён ответом
  | { _tag: 'AwaitUser'; prompt: string }         // требуется ввод или подтверждение пользователя
  | { _tag: 'Continue';  next: RouterInput };     // трамплин: запросить маршрутизатор ещё раз (внутри хода)

interface FunctionDefinition<A> {
  readonly name: string;
  readonly description: string;
  readonly args: z.ZodType<A>;                    // схема аргументов; из неё строится описание для модели
  readonly run: (args: A, ctx: FunctionContext) => Effect.Effect<TurnResult>;
}

type FunctionContext = {
  readonly state: DialogState;                    // сводка состояния, только чтение
  readonly patchState: (f: (s: DialogState) => DialogState) => Effect.Effect<void>;
  readonly runChild: <I, O>(job: Job<I, O>, key: JobKey, input: I) => Effect.Effect<O>; // запуск устойчивой джобы
  readonly status: (message: string) => Effect.Effect<void>;  // промежуточное сообщение о состоянии
};
```

## 3. Вариант A — цикл в обработчике запроса (минимальный, недолговечный)

Ход исполняется непосредственно в обработчике HTTP-запроса как обычное Effect-вычисление.
Новых таблиц нет; состояние доски — одна строка, лента — массив в ней же.

```
POST /board/:id/message ──▶ выполнение хода в памяти процесса
                               цикл: маршрутизатор → диспетчеризация → TurnResult
                               тяжёлая работа: запуск дочерней джобы с ожиданием
                            ◀── ответ в том же HTTP-ответе
```

**Достоинства:** минимум кода (порядка одного дня работы после доработки транспорта);
идеален для проверки гипотез — качества маршрутизации YandexGPT, формы схем функций,
текста системного промпта.

**Недостатки:** ход не переживает перезапуск — при падении сервера во время долгой
операции сама работа и её результаты сохранятся (за счёт однократной отправки в дочерних
джобах), однако ответ пользователю в чат не придёт; долгий ход удерживает HTTP-соединение;
одновременная переписка невозможна.

**Роль в итоговой схеме:** не целевая архитектура, а разведочный прототип. Его назначение —
проверить транспорт и качество маршрутизации до того, как строить устойчивый контур.
Цикл и реестр функций затем переносятся в вариант B без изменений; заменяется только
способ запуска.

## 4. Вариант B — ход как джоба: устойчивый трамплин (ядро решения)

Вариант, к которому пришло обсуждение. Ход разговора оформляется как корневая джоба;
состояние трамплина сохраняется в её памяти; вся диалоговая механика живёт в том же
фреймворке задач, без параллельного «лёгкого» мира.

```
DialogTurnJob  (запуск JobRun, ключ = ['board', boardId, 'turn', turnIndex])
 │
 │  Memo (память джобы): steps: Array<{ fn, args, resultRef }>   ← журнал шагов трамплина
 │
 ├─ шаг 0: JobTools.run(FunctionRouterTool, key=['router','0'])
 │            решение записывается в ToolMemo ДО исполнения (однократная отправка)
 │            └─ диспетчеризация → FunctionDefinition.run
 │                 ├─ лёгкая функция: исполняется на месте → Reply
 │                 └─ тяжёлая: Jobs.run(дочерняя джоба, стабильный ключ) — с ожиданием;
 │                    при возобновлении происходит присоединение к уже идущему запуску
 ├─ шаг 1: … (если предыдущий шаг вернул Continue)
 └─ завершение → Reply / AwaitUser → запись в ленту, обновление DialogState
```

Свойства варианта:

- **Ход устойчив.** Если сервер перезапустился на пятнадцатой минуте анализа,
  восстановление незавершённых запусков при старте приложения воскресит `DialogTurnJob`;
  трамплин продолжится с последнего шага, решения маршрутизатора будут взяты из памяти,
  дочерняя джоба присоединится по хешу ключа, и ответ дойдёт до пользователя. Главный
  недостаток варианта A устранён.
- **Накладные расходы несущественны.** Возражение «заводить джобу на каждый элемент
  дорого» относилось к конвейеру подготовки документов, где элементов много и они мелкие.
  В чате реплики приходят с частотой раз в несколько секунд; вставка строки `JobRun`
  и записи в память занимают миллисекунды.
- **Механизм прогресса достаётся даром.** Ход — это джоба, следовательно, у него есть
  `Progress`; промежуточные сообщения хода идут по штатному механизму, который интерфейс
  уже умеет отображать (дерево запусков).
- **Один фреймворк.** Идемпотентность по хешу ключа, возобновление, `Swarm`, учётная
  книга токенов и её атрибуция (`withTokensUsageScope({ boardId, turnIndex })`)
  переиспользуются без изменений.

Что необходимо проверить в коде до начала реализации:

- [ ] поведение `Jobs.run` при уже существующем хеше ключа: происходит ли присоединение
      к идущему запуску (а не ошибка и не дублирование);
- [ ] виден ли `Progress` из тела `DialogTurnJob` снаружи в реальном времени;
- [ ] ограничители: предел числа шагов трамплина и предельный срок хода, переживающий
      возобновление (урок C2 из `dps-audit.md`: момент старта следует хранить в памяти
      джобы, а не в памяти процесса).

**Ограничение варианта B в чистом виде:** он описывает исполнение хода, но не отвечает
на два вопроса продукта: как интерфейс отображает разговор и что происходит, когда
пользователь пишет во время исполняющегося хода. Ответы даёт вариант C.

## 5. Вариант C — доска как лента записей (разговор — это данные)

Иной взгляд: не строить «исполняющую машину чата» вовсе. Доска — это таблица записей,
пополняемая только добавлением. Отправить сообщение — значит вставить строку; обработка —
это реакция на появление строки; интерфейс — обычное чтение таблицы.

```
таблица boards:       id, orderId, state (DialogState в JSON), createdAt…
таблица board_turns:  id, boardId, index, author (user|assistant|system),
                      kind (message|status|reply|await_user), payload, jobRunId?, createdAt

POST /board/:id/message
  └─ вставка строки (user, message)            ← единственное действие HTTP-слоя
  └─ запуск Jobs.run(DialogTurnJob, ['board', id, 'turn', index])   ← исполнитель — вариант B

DialogTurnJob в ходе работы:
  └─ промежуточные состояния → вставка строк (system, status)
  └─ завершение → вставка строки (assistant, reply | await_user) + обновление boards.state

GET /board/:id/turns (опрос или SSE)            ← интерфейс просто читает ленту
```

Что этот вариант добавляет к варианту B:

- **Интерфейс тривиален.** Экран чата — это список строк `board_turns`. Отдельный
  протокол доставки состояния хода не нужен: сообщения о ходе работы — такие же строки
  ленты. Подробный прогресс дочерних джоб уже доступен через существующее дерево
  запусков (у хода есть `jobRunId`).
- **Одновременная переписка сводится к политике очереди, а не к архитектуре.** Если
  пользователь написал во время исполняющегося хода, строка просто ложится в ленту,
  а дальше действует выбранная политика (её можно менять, не перестраивая систему):
  - *последовательная обработка* — ходы исполняются строго по порядку индексов ленты;
    просто и предсказуемо; рекомендуемое начало;
  - *прерывание* — новое сообщение отменяет текущий ход (прерывание Effect-вычисления
    джобы) и начинает новый; полезно для «стой, не то»; добавить позже;
  - *дополнение* — новое сообщение вливается в контекст текущего хода; **не делать**:
    усложняет семантику возобновления, а выигрыш сомнителен.
- **Разбор инцидентов и аудит.** Лента, журналы шагов ходов и трассы Langfuse вместе
  дают полную картину: что сказал пользователь, что решил маршрутизатор, что сделала
  система. Разговор восстановим целиком постфактум.
- **Единая входная дверь.** Программный запуск анализа (кнопка интерфейса, внешний API) —
  это синтетическая запись в ленту вида `{ kind: 'command', fn: 'analyzeOrder', args }`,
  которую маршрутизатор пропускает без обращения к модели (детерминированный короткий
  путь). Один реестр возможностей обслуживает все входы; отдельные контроллеры запуска
  джоб постепенно упраздняются.

**Цена:** две новые таблицы с миграциями и несколько больше кода на старте, чем
в варианте A. Однако каждая часть плоская: лента — обычные операции с таблицей,
обработчик — вариант B, политика — перечисление.

## 6. Вариант D — план вместо пошаговых решений (режим, а не архитектура)

Для составных команд («проанализируй заказ и покажи проблемные позиции») маршрутизатор
может одним обращением к модели вернуть небольшой план — массив вызовов функций
(структурированный вывод: `steps: Array<{ fn, args }>`), — который цикл затем исполняет
детерминированно, не обращаясь к модели между шагами.

- Достоинства: дешевле по токенам (одно обращение вместо нескольких); план можно
  показать пользователю до исполнения — естественная точка подтверждения разрушающих
  действий; исполнение полностью детерминировано.
- Недостатки: план строится вслепую, не видя результатов промежуточных шагов;
  ветвление вида «если позиций нет — сначала извлеки» требует трамплина.
- Вывод: это не альтернатива, а оптимизация внутри вариантов B и C. Начинать следует
  с чистого трамплина: одно решение за раз проще отлаживать, и такой режим надёжнее
  для YandexGPT. Режим плана стоит добавить позже отдельной функцией в том же реестре,
  если наблюдения (Langfuse) покажут частые однотипные цепочки. Заранее не закладывать.

## 7. Сравнение и рекомендация

| Критерий | A: в обработчике | B: ход-джоба | C: лента + B | D: план |
|---|---|---|---|---|
| Ход переживает перезапуск | нет | да | да | — (режим) |
| Отображение разговора | не решено | не решено | тривиально (лента) | — |
| Письмо во время работы | нет | нет (нет очереди) | да (политика) | — |
| Понятность, плоскость слоёв | высокая | высокая | высокая (3 плоских слоя) | высокая |
| Новые таблицы | 1 | 1 | 3 | 0 |
| Срок до первого диалога | дни | около недели | 1–2 недели | добавляется позже |
| Судьба кода при развитии | цикл и реестр переносятся | становится ядром C | целевая форма | — |

**Рекомендация — не выбор одного варианта, а последовательность, сходящаяся к цели:**

1. **Разведка по варианту A (дни).** Доработать транспорт (передача `tools`, разбор
   `function_call`), собрать реестр из трёх-четырёх функций (`answer`, `editPosition`,
   `analyzeOrder`, `showPositions`), цикл в обработчике, и проверить качество
   маршрутизации YandexGPT на реальных формулировках. Способность модели уверенно
   выбирать функцию — главный риск всей затеи; его следует снять раньше, чем строить
   архитектуру.
2. **Ядро по варианту B.** Перенести цикл в `DialogTurnJob` с журналом шагов в памяти
   джобы; закрыть контрольный список из §4 (присоединение по хешу ключа, срок в памяти,
   предел шагов).
3. **Оболочка по варианту C.** Лента `board_turns`, последовательная политика очереди,
   чтение лентой в интерфейсе; синтетические записи вместо прямого запуска джоб.
4. **Вариант D — только по результатам наблюдений** из Langfuse.

Langfuse (через порт `LlmUsageSink`) следует подключить **до шага 1**: тогда уже
разведочный прототип даст трассы решений маршрутизатора, по которым и будет оцениваться
качество.

Целевая картина после шага 3:

```
HTTP/интерфейс ──▶ board_turns (лента, только добавление) ──▶ DialogTurnJob (устойчивый трамплин)
                                                                 │
                                                                 ├─ FunctionRouterTool (одно решение модели,
                                                                 │   сохраняемое до исполнения)
                                                                 └─ реестр FunctionDefinition
                                                                       ├─ лёгкие функции → Reply / AwaitUser
                                                                       └─ Jobs.run(существующие джобы) — без изменений
```

Четыре плоских слоя; каждый — либо данные, либо уже существующий примитив фреймворка.
Новых абстракций ровно три: лента, `DialogTurnJob`, `FunctionDefinition`. Всё остальное —
переиспользование (`JobTool`, `ToolMemo`, `Swarm`, учётная книга токенов, дерево запусков
в интерфейсе).

## 8. Открытые вопросы владельцу (до начала шага 2)

1. Политика очереди на старте: подтверждается ли последовательная обработка ходов?
2. Объём сводки `DialogState`: весь заказ или окно (например, только позиции, упомянутые
   в последних K ходах, плюс счётчики)? От этого зависит расход токенов маршрутизатора
   на больших заказах.
3. Где хранить «сведения от пользователя» («материал всегда 12Х18Н10Т, если не сказано
   иное»): в `DialogState` доски или в отдельном справочнике заказа? Предложение:
   в поле `DialogState.facts` (плоский список строк, подаваемый маршрутизатору) —
   до тех пор, пока этого не станет мало.
4. Подтверждения `AwaitUser`: сбрасывается ли ожидающее подтверждение, если следующий
   ход посвящён другой теме, или оно живёт до явного отказа? Предложение: сбрасывать
   при любом ходе, не являющемся ответом на подтверждение, — такая модель проще
   для понимания.
