# Памятка: работа с миграциями Prisma

> Практическое руководство по управлению схемой базы данных. Рассчитано на читателя без
> предыдущего опыта работы с миграциями. Общий план перехода на Prisma — в
> [`README.md`](./README.md); здесь — только повседневная работа со схемой.

---

## 1. Базовая ментальная модель

У Prisma есть **один источник правды** — файл `back-nest/prisma/schema.prisma`. В нём
описаны модели (таблицы). Задача любого инструмента миграции — привести **реальную базу**
в соответствие с тем, что написано в схеме.

Существуют два принципиально разных способа это сделать. Выбор между ними зависит от
одного обстоятельства: **есть ли в базе данные, которые нельзя потерять.**

| | Данные не важны (dev) | Данные нужно сохранить (prod) |
|---|---|---|
| Инструмент | `prisma db push` | `prisma migrate` |
| История изменений | не ведётся | версионируемые SQL-файлы в `prisma/migrations/` |
| Безопасность данных | может пересоздать таблицы | контролируемая, с ручной правкой при необходимости |

Главное, что нужно усвоить: **миграция Prisma — это обычный SQL-файл**. Никакой магии.
Когда говорят «ручная миграция», имеют в виду, что этот файл отредактировали руками.
«Призмовских» и «ручных» миграций как двух разных сущностей не существует — это один и тот
же файл, который Prisma либо сгенерировала полностью сама, либо вы поправили.

## 2. Режим разработки: пока данных нет

Это режим, в котором проект находится **сейчас**. Файлы миграций не нужны вообще.

### Цикл работы

```
1. Меняешь schema.prisma (добавил поле, модель, изменил тип)
2. npm run prisma:push      # Prisma приводит базу к виду схемы
3. Работаешь дальше
```

`db push` сравнивает схему с базой и applies разницу напрямую. Если изменение
разрушительное (например, удаление колонки с данными), Prisma предупредит и спросит
подтверждение — но в dev-режиме это не страшно, данные тестовые.

### Когда что-то пошло не так

Если база пришла в странное состояние или хочется начать с чистого листа:

```
npm run prisma:reset        # полностью сбрасывает базу, накатывает схему заново + seed
```

Если нужно сбросить вообще всё, включая том Docker (например, повредился volume):

```
npm run db:reset-hard       # docker compose down -v — удаляет контейнер и том
npm run db:up               # поднять контейнер заново (пустая база)
npm run prisma:push         # накатить схему
npm run prisma:seed         # наполнить тестовыми данными
```

### Что важно помнить в этом режиме

- **Не создавай файлы миграций.** Каталога `prisma/migrations/` пока быть не должно.
- После каждого `db push` Prisma автоматически перегенерирует клиент. Если этого не
  произошло (редко) — `npm run prisma:generate` вручную.
- `db push` не ведёт историю. Откатиться к «предыдущей схеме» нельзя — только переписать
  схему обратно и снова `push`. На стадии разработки это приемлемо.

## 3. Переход к версионируемым миграциям

С момента, когда появляется окружение с **реальными данными, которые нельзя потерять**
(первый production-деплой, демо-стенд с введёнными данными), режим `db push` оставляют
позади и переходят на версионируемые миграции.

### Однократная инициализация

```
npm run prisma:migrate -- --name init
```

Эта команда:

1. создаёт каталог `prisma/migrations/<timestamp>_init/`;
2. кладёт туда `migration.sql` — полный SQL для создания текущей схемы;
3. применяет его к базе;
4. записывает факт применения в служебную таблицу `_prisma_migrations`.

С этого момента каждое изменение схемы оформляется новой миграцией.

### Обычное изменение схемы

```
1. Меняешь schema.prisma
2. npm run prisma:migrate -- --name add_user_phone
3. Prisma генерирует новый SQL-файл и применяет его
```

`--name` — короткое описание изменения в snake_case. Оно попадёт в имя каталога миграции,
поэтому делай его осмысленным (`add_user_phone`, а не `update`).

### Применение на production

На production-сервере **никогда не запускают** `migrate dev` (он умеет генерировать и
может задавать вопросы). Там применяют только уже готовые миграции:

```
prisma migrate deploy       # применяет ожидающие миграции, ничего не генерирует
```

Эта команда идемпотентна: применяет только те миграции, которых ещё нет в
`_prisma_migrations`. Запускается обычно в составе деплой-скрипта перед стартом приложения.

## 4. Миграции с сохранением данных («ручные»)

Это и есть то, ради чего существует вся §3. Иногда Prisma по умолчанию генерирует SQL,
который уничтожит данные, хотя цель — их сохранить. Тогда миграцию правят руками.

### Почему это вообще нужно

Prisma не всегда понимает **намерение**. Самый частый пример — переименование колонки.
Для Prisma `было поле A, стало поле B` выглядит как «удалить A, добавить B», и она
сгенерирует:

```sql
ALTER TABLE "users" DROP COLUMN "name";
ALTER TABLE "users" ADD COLUMN "fullName" TEXT;
```

Данные из `name` при этом пропадут. А намерение было — **переименовать**, сохранив данные.

### Рабочий приём: `--create-only`

Ключ `--create-only` говорит Prisma: «сгенерируй SQL-файл, но **не применяй** его». Это
даёт окно, чтобы отредактировать SQL перед накатом.

```
1. Меняешь schema.prisma (например, переименовал поле)
2. npm run prisma:migrate -- --create-only --name rename_name_to_full_name
   # → создан prisma/migrations/<...>_rename_name_to_full_name/migration.sql, НЕ применён
3. Открываешь migration.sql и правишь его руками
4. npm run prisma:migrate
   # → теперь Prisma применяет отредактированный файл
```

Для примера с переименованием заменяешь сгенерированный `DROP`/`ADD` на:

```sql
ALTER TABLE "users" RENAME COLUMN "name" TO "fullName";
```

### Рецепты типовых сценариев

**Переименование колонки** — заменить `DROP`/`ADD` на `RENAME`:

```sql
ALTER TABLE "users" RENAME COLUMN "name" TO "fullName";
```

**Добавление NOT NULL-колонки к таблице с данными** — нельзя добавить NOT NULL без
значения по умолчанию, иначе существующие строки нарушат ограничение. Решается в три шага
(паттерн expand → migrate → contract):

```sql
-- Миграция 1: добавить как nullable
ALTER TABLE "orders" ADD COLUMN "status" TEXT;

-- Backfill: заполнить существующие строки
UPDATE "orders" SET "status" = 'draft' WHERE "status" IS NULL;

-- Миграция 2 (отдельная): сделать NOT NULL
ALTER TABLE "orders" ALTER COLUMN "status" SET NOT NULL;
```

**Разбиение/перенос данных между таблицами** — добавить новую структуру, перенести
данные, отдельной миграцией удалить старую:

```sql
INSERT INTO "profiles" ("userId", "bio")
SELECT "id", "bio" FROM "users" WHERE "bio" IS NOT NULL;
-- удаление старой колицы — следующей миграцией, после проверки переноса
```

### Главное правило data-preserving миграций

Никогда не оставляй удаление данных и их перенос в **одной** миграции, если перенос может
не сработать. Сначала миграция, которая добавляет новое и переносит данные. Проверяешь
результат. Только потом — отдельная миграция, удаляющая старое. Это даёт точку отката.

## 5. Полезные команды и инструменты

| Команда | Назначение |
|---|---|
| `npm run prisma:studio` | GUI-просмотр и редактирование данных в браузере |
| `npm run prisma:generate` | Перегенерировать клиент вручную (обычно делается автоматически) |
| `npm run prisma:push` | Синхронизировать схему с базой (dev-режим, без миграций) |
| `npm run prisma:reset` | Сбросить базу и накатить схему/миграции + seed |
| `npm run prisma:migrate -- --name <имя>` | Создать и применить миграцию (когда уже на миграциях) |
| `npm run prisma:migrate -- --create-only --name <имя>` | Сгенерировать миграцию без применения (для ручной правки) |
| `prisma migrate deploy` | Применить ожидающие миграции (production) |
| `prisma migrate status` | Показать, какие миграции применены, какие ожидают |

`prisma:studio` особенно полезен на старте: позволяет глазами увидеть, что реально лежит в
таблицах, без написания SQL.

## 6. Типичные грабли

- **Запустил `db push` на базе с миграциями** — `db push` и `migrate` не дружат на одной
  базе. После перехода на миграции (§3) `db push` больше не используют. Смешение приводит
  к рассинхрону `_prisma_migrations` и реальной схемы.
- **Применил `migrate dev` на production** — `migrate dev` предназначен только для
  локальной разработки. На production — строго `migrate deploy`.
- **Забыл `dotenv -e ../.env`** — CLI Prisma не увидит `DATABASE_URL` (он в корневом
  `.env`, а Prisma ищет рядом со схемой). Все скрипты в `package.json` уже обёрнуты в
  `dotenv-cli` — запускай через `npm run prisma:*`, а не голым `prisma`.
- **Отредактировал уже применённую миграцию** — нельзя. Применённые миграции
  неизменяемы (их хеш записан в `_prisma_migrations`). Изменение схемы — всегда **новая**
  миграция, а не правка старой.
- **Удалил каталог `prisma/migrations/` на проекте, который уже на миграциях** — потеряешь
  историю и рассинхронизируешь production. Удаление миграций допустимо только в dev до
  первого реального деплоя.
- **`--name` забыт** — Prisma спросит имя интерактивно. В скриптах всегда передавай `--name`
  явно, иначе команда зависнет в ожидании ввода.

## 7. Краткая шпаргалка «что делать сейчас»

Пока база пустая и проект в разработке (текущий момент):

```
# изменил схему?
npm run prisma:push

# насорил данными / база в странном состоянии?
npm run prisma:reset

# хочу посмотреть данные?
npm run prisma:studio
```

**Файлы миграций не трогаем.** Всё, что в §3–4, — на будущее, когда появится production с
реальными данными. До этого момента читать §3–4 не обязательно.
