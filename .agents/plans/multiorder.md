# Multiorder — обработка таблиц с несколькими позициями

## Контекст задачи

Клиенты присылают заявки в виде Excel-таблиц с 20–270 строками и 2–21 столбцом.
Формат таблиц всегда разный — нет стандарта. Одни делают тендерные формы на 21 столбец,
другие — простой список в 2 столбца, третьи — выгрузку из ERP на 267 позиций.

Уже есть пайплайн для обработки **одной** позиции продукции. Задача — научиться
вычленять **массив позиций** из произвольной таблицы и загонять каждую в существующий пайплайн.

Из каждой позиции нужно извлечь:
- **Продукция** — общее название
- **Тип продукции** — есть в нашей номенклатуре или не изготавливаем
- **Требования** — технические параметры, если указаны

## Выбранный подход — двухфазная обработка

### Почему не «один большой вызов»

Для таблиц до ~50 строк — работает. Для 200+ строк выход за лимит токенов по выходу
(267 JSON-объектов не влезают). Нужно дробить.

### Почему не агент с tool calling

Агент сам управляет петлёй (решает что читать дальше). Это оправдано когда нужна
навигация — когда нельзя знать заранее что читать. Для таблицы, которая уже целиком
есть — навигация не нужна. Агент добавляет сложность, дороже, нет гарантии что
обработает все строки. Двухфазный подход надёжнее и дешевле.

## Архитектура двухфазной обработки

### Фаза 1 — определение структуры (1 LLM-вызов)

Скормить первые 10–15 строк таблицы (шапка + начало данных).
LLM возвращает не данные, а **схему чтения таблицы**:

```json
{
  "headerRow": 16,
  "dataStartRow": 17,
  "dataEndRow": 34,
  "columns": {
    "productName": 1,
    "specs": 2,
    "quantity": 5,
    "unit": 4
  },
  "skipWhen": "первый столбец пустой или содержит 'Итого'"
}
```

Схему можно кешировать на уровне файла — если клиент шлёт одинаковый шаблон повторно,
платишь за структурный анализ один раз.

### Фаза 2 — извлечение позиций (N LLM-вызовов батчами)

Код вычитывает строки данных по схеме из Фазы 1.
Строки группируются в батчи по **3–5 штук** и отправляются в LLM.

Каждый вызов получает:
- Заголовки столбцов (из схемы) — чтобы LLM понимал семантику каждой ячейки
- N строк данных

Возвращает:
```json
[
  {
    "productName": "Переход с приварными катушками 219х6,0...",
    "requirements": [
      { "parameterName": "ГОСТ", "requiredValue": "17378-2001" },
      { "parameterName": "Кол-во", "requiredValue": "4 шт" }
    ]
  }
]
```

### Количество вызовов

| Таблица | Строк | Фаза 1 | Фаза 2 (батч 4) | Итого |
|---|---|---|---|---|
| Форма КП | 18 | 1 | 5 | **6** |
| Запрос на СДТ | 8 | 1 | 2 | **3** |
| Копия ИПЦ | 267 | 1 | 67 | **68** |

## Общая схема пайплайна

```
Excel / PDF
    ↓
Extraction (OCR / spreadsheet parser) — уже есть
    ↓
TableStructureWorker — Фаза 1
  Вход: первые 15 строк таблицы
  Выход: схема (columnMapping, dataRange, skipRules)
    ↓
Код: вычитать строки данных по схеме → батчи по 3-5 строк
    ↓
TableItemsWorker — Фаза 2 (по батчу)
  Вход: заголовки + батч строк
  Выход: [{productName, requirements[]}]
    ↓
Существующий пайплайн × количество позиций
```

## Особые случаи

### Запрос на СДТ — несколько позиций в одной ячейке
В Фазе 1 LLM определяет что позиции разделены `\n` внутри одной ячейки.
В Фазе 2 промпт должен учитывать это: «одна строка может содержать несколько позиций,
разверни их в отдельные объекты».

### ERP-выгрузки (тип Копии ИПЦ)
Структура идеальная и машиночитаемая. Фаза 1 всё равно нужна (унификация),
но схема будет простейшей. Альтернатива — детектировать программно
(если >80% строк в колонке № числовые → Фаза 1 тривиальная, можно упростить).
