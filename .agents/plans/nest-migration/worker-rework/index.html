Цель переработки — превратить воркеры из многословных классов, где 70 % кода занимает повторяющаяся церемония, в небольшие надёжные задачи, которые легко соединять в цепочки. Инструментом выбран Effect. Эта страница сперва объясняет, из чего складываются его примитивы и почему они устроены так, а лишь затем приходит к нашей конструкции — задаче (англ. Job) и пайплайну (англ. pipeline) с восстановлением после сбоя.

1Зачем «эффект как значение»

Представим привычный асинхронный код. Когда мы пишем const text = await fetchText(), происходит сразу несколько вещей, и все они неявные. Во-первых, побочное действие (запрос в сеть) запускается немедленно — выражение нельзя «подержать в руках», не выполнив его. Во-вторых, тип результата — string, и из него никак не видно, что вызов может выбросить ошибку. В-третьих, откуда взялся fetchText — из импорта; то есть зависимость зашита намертво и в тесте её трудно подменить. В-четвёртых, прервать такой вызов извне нельзя.

Effect предлагает иной взгляд: программа — это описание вычисления, а не само вычисление. Значение типа Effect<A, E, R> читается как «программа, которая при запуске даст значение A, может завершиться ошибкой E и требует для работы окружение R». Пока программу не запустили, она остаётся обычным значением: его можно передавать, комбинировать, оборачивать и видоизменять.

Почему такТри буквы A, E, R — это и есть тот честный контракт, которого не хватает в async/await: что вернётся, чем может упасть и что для этого нужно. Компилятор начинает следить за ошибками и зависимостями так же строго, как за обычными типами, — а значит, целый класс оплошностей по невнимательности отлавливается ещё до запуска.

2Создание эффектов: примитивы

Эффекты не создаются «из воздуха» — для каждого источника значения есть свой конструктор. Их несколько именно для того, чтобы тип точно отражал природу шага: чистый он или способен упасть.

import { Effect } from 'effect';

// готовое значение — никогда не падает
const a = Effect.succeed(42);              // Effect<number>
const e = Effect.fail(new NotFound());     // Effect<never, NotFound>

// чистая синхронная функция без выбросов
const now = Effect.sync(() => Date.now());  // Effect<number>

// промис, который НЕ должен падать (ошибку считаем дефектом)
const p = Effect.promise(() => readClock());    // Effect<Date>

// промис, ошибку которого ловим в типизированный канал E
const t = Effect.tryPromise({
  try: () => fetch(url),
  catch: (cause) => new NetworkError({ cause }),
});                                       // Effect<Response, NetworkError>
Почему несколько конструкторовРазделение promise и tryPromise заставляет в момент написания ответить на вопрос «а может ли этот шаг провалиться?». Если да — ошибка немедленно появляется в типе E и её нельзя молча забыть. Если нет — мы это явно декларируем.

3Запуск: эффект ленив

Ключевое следствие «эффекта как значения»: пока его не запустили, ничего не происходит. Запуск — отдельный, обычно единственный, шаг на краю программы.

const result = await Effect.runPromise(program);   // выполнить и получить промис
const fiber  = Effect.runFork(program);          // запустить «волокно» в фоне
Почему это важно для насЛенивость означает, что задачу можно собрать, проверить типами, обернуть в повтор и отдать раннеру — и лишь он решит, когда и как её исполнить. Именно это позволит нам останавливать, возобновлять и сохранять прогресс, не переписывая саму задачу.

4Композиция: map, flatMap, pipe

Маленькие эффекты соединяются в большие. map преобразует успешное значение; flatMap сцепляет шаг, который сам возвращает эффект (то есть зависимый от предыдущего). Чтобы цепочки читались сверху вниз, Effect использует «данные последним аргументом» и функцию pipe.

// flatMap сцепляет зависимые шаги, но в цепочке рождается «лесенка»
const len = Effect.flatMap(fetchUser, (user) =>
  Effect.flatMap(fetchOrders(user.id), (orders) =>
    Effect.succeed(orders.length)));

// pipe выпрямляет запись: «значение, затем операции над ним»
const len2 = fetchUser.pipe(
  Effect.flatMap((user) => fetchOrders(user.id)),
  Effect.map((orders) => orders.length),
);

Даже с pipe длинные зависимые цепочки остаются неудобными: каждый следующий шаг хочет видеть результаты всех предыдущих. Эту проблему решают генераторы.

5Генераторы: Effect.gen и yield*

Это главный приём, на котором держится вся дальнейшая конструкция. Effect.gen позволяет писать последовательный зависимый код плоско — почти как async/await, — но результат остаётся значением типа Effect. Оператор yield* «извлекает» успешное значение вложенного эффекта; если тот падает, выполнение генератора прекращается, и ошибка уходит в канал E.

const program = Effect.gen(function* () {
  const user   = yield* fetchUser;            // извлекаем успех
  const orders = yield* fetchOrders(user.id);  // шаг зависит от предыдущего
  return orders.length;                       // обычный return — это успех A
});
Почему генераторы, а не async/awaitВнешне похоже, но разница принципиальна: await немедленно запускает и теряет тип ошибки, а yield* лишь описывает шаг внутри значения-эффекта. Поэтому ошибки и зависимости каждого yield* аккуратно накапливаются в итоговом типе Effect<A, E, R>, а сам блок можно повторять, прерывать и комбинировать как любое другое значение.

6Типизированные ошибки

Ошибка в Effect — не выпавшее откуда-то исключение, а часть сигнатуры. Удобнее всего описывать ошибки как помеченные классы: тогда их можно различать по «метке» (англ. tag) и обрабатывать выборочно.

import { Data, Effect } from 'effect';

class NetworkError extends Data.TaggedError('NetworkError')<{ cause: unknown }> {}
class NotFound     extends Data.TaggedError('NotFound')<{ id: string }> {}

const safe = program.pipe(
  Effect.catchTag('NotFound', (err) => Effect.succeed(fallbackFor(err.id))),
  // NetworkError намеренно оставляем — пусть всплывает выше
);
Почему это снижает ошибки по невнимательностиЕсли шаг может вернуть NotFound, это написано в его типе. Забыть обработать такую ситуацию нельзя молча — компилятор будет видеть необработанную ошибку в канале E до самого края программы.

7Зависимости: Context и Layer

Вместо того чтобы импортировать сервис как глобальный одиночка (англ. singleton), в Effect зависимость объявляется тегом (Context.Tag). Когда эффект обращается к тегу, требование автоматически попадает в третий канал типа — R. Конкретную реализацию подставляют «слоем» (Layer) в момент запуска.

import { Context, Effect, Layer } from 'effect';

// объявляем зависимость как тег с её интерфейсом
class Llm extends Context.Tag('Llm')<Llm, {
  submit(req: SubmitReq): Promise<string>;
  poll(opId: string): Promise<{ done: boolean; result?: TcRules }>;
}>() {}

// обращение к зависимости внутри эффекта — требование уходит в канал R
const ask = Effect.gen(function* () {
  const llm = yield* Llm;                  // Effect<..., ..., Llm>
  return yield* Effect.promise(() => llm.submit(req));
});

// реализацию подставляем слоем — здесь же мост из Nest
const LlmLive = Layer.succeed(Llm, nestYandexLlmService);  // объект-реализация
const runnable = ask.pipe(Effect.provide(LlmLive));         // R закрыт → можно запускать
Мост Nest ↔ EffectВ нашем случае реализацию тега даёт обычный Nest-провайдер: фабрика (которую мы и договорились использовать) инжектит нужные сервисы и заворачивает их в Layer. Так Effect отвечает за композицию задач, а Nest — за жизненный цикл и внедрение зависимостей; границы не пересекаются.

8Расписания и повтор: Schedule

«Когда повторять» в Effect — это отдельное композируемое описание, Schedule. Его можно соединять с любым эффектом через repeat (повторять успех) или retry (повторять при ошибке).

import { Effect, Schedule } from 'effect';

Schedule.spaced('3 seconds');     // фиксированная пауза между попытками
Schedule.exponential('1 second'); // растущая пауза (для retry внешних сбоев)
Schedule.recurs(5);              // не более пяти повторов

// повторять опрос с паузой, пока не вернётся done=true
const awaited = checkOnce.pipe(
  Effect.repeat({ schedule: Schedule.spaced('3 seconds'), until: (r) => r.done }),
);
Почему отдельноЛогика «что делаем» (один опрос) и политика «как часто и до каких пор» (расписание) развязаны. Поэтому один и тот же опрос можно повторять с разной стратегией, не трогая его код, — а сами стратегии переиспользовать между задачами.

9Отмена (прерываемость)

Эффекты прерываемы по своей природе: между шагами Effect может корректно остановить вычисление, освободив ресурсы. Не нужно вручную тащить флаг вроде shouldStop, как в нынешних воркерах.

// прервать, если не уложились в срок
const bounded = program.pipe(Effect.timeout('30 seconds'));

// запустить в фоне и прервать извне
const fiber = Effect.runFork(program);
await Effect.runPromise(Fiber.interrupt(fiber));
Связь с восстановлениемПрерывание останавливает вычисление, но не стирает то, что мы уже сохранили на диск. Если задача успела записать контрольную точку (см. раздел 13), после отмены или падения процесса она продолжится именно с неё.

10Job как Effect

Теперь соберём из оснований нашу единицу работы. Job — это функция, превращающая вход в эффект, дающий выход:

type Job<I, O, R = never> = (input: I) => Effect.Effect<O, JobError, R>;

Поскольку тело Job — это Effect.gen, внутри него можно вызывать другие Job через yield*. Значит, цепочка задач — это снова Job. Композиция рекурсивна и единообразна: «атом» и «конвейер» имеют один тип, и пайплайн всегда можно вложить в больший пайплайн.

const loadTcText:  Job<{ tcId: string }, { text: string }, Files> = (/* ... */) => /* ... */;
const applyTcRules: Job<TcRules, void, Tc>                     = (/* ... */) => /* ... */;

// пайплайн — это тоже Job: вход первого, выход последнего
const tcDetailsJob: Job<{ tcId: string }, void, Files | Tc | Llm | Checkpoint> =
  ({ tcId }) => Effect.gen(function* () {
    const { text } = yield* loadTcText({ tcId });
    const rules    = yield* tcDetailsLlm({ text });   // см. раздел 11
    yield* applyTcRules(rules);
  });
Что мы выигралиСтыки проверяет компилятор: выход loadTcText обязан совпасть со входом следующего шага. Все требуемые зависимости (Files | Tc | Llm | Checkpoint) собираются в канале R автоматически — забыть подключить сервис не выйдет, программа просто не запустится без нужного слоя.

11Комбинатор poll

Опрос длительной облачной операции встречается в нескольких воркерах. Вынесем его в один переиспользуемый кирпич, собранный из Schedule и repeat. Любая задача затем строит свой опрос из него, не переписывая цикл.

const pollUntilDone = <O>(opId: string) => Effect.gen(function* () {
  const llm = yield* Llm;
  const last = yield* Effect.tryPromise({
    try: () => llm.poll<O>(opId),
    catch: (cause) => new PollError({ opId, cause }),
  }).pipe(
    Effect.repeat({ schedule: Schedule.spaced('3 seconds'), until: (r) => r.done }),
  );
  return last.result!;
});

Это и есть «отдельная область, переиспользуемая каждым воркером», о которой шла речь: pollUntilDone ничего не знает о конкретной задаче — только о том, как опрашивать операцию по её идентификатору.

12Прогресс

Чтобы наблюдать ход работы, заведём ещё один сервис в контексте — Progress. Задача сообщает о фазах, а раннер агрегирует прогресс по всему пайплайну (завершённые этапы плюс прогресс текущего). Снаружи (HTTP, интерфейс) прогресс читается из записи прогона.

class Progress extends Context.Tag('Progress')<Progress, {
  report(p: { phase: string; pct?: number }): Effect.Effect<void>;
}>() {}

// внутри опроса можно докладывать фазу
const step = Effect.gen(function* () {
  const progress = yield* Progress;
  yield* progress.report({ phase: 'polling' });
  // ...
});
ЗамечаниеПрогресс — это наблюдаемость, а не состояние для возобновления. Для восстановления служат контрольные точки (следующий раздел); прогресс лишь показывает, на каком шаге мы сейчас.

13Долговечность и контрольные точки

Это центральный раздел. Effect прекрасно описывает вычисление, но его «волокно» живёт в оперативной памяти: если процесс упал посреди опроса, волокно исчезает. А у нас жёсткое требование — пережить перезапуск и продолжить работу (нынешний механизм restore()). Значит, слой долговечности (англ. durability) мы строим сами, поверх Effect.

Что именно мы храним

На каждый запуск пайплайна заводится запись прогона в нашей JsonCollection. Она хранит курсор (индекс текущего этапа) и состояние каждого этапа — статус, выход (для завершённых) и контрольную точку (для незавершённого).

type StageState =
  | { status: 'pending' }
  | { status: 'running'; checkpoint: Record<string, unknown> }
  | { status: 'done'; output: unknown }
  | { status: 'failed'; error: string };

type PipelineRun = {
  id: string; pipeline: string; input: unknown;
  cursor: number;            // индекс текущего этапа
  stages: StageState[];      // по одному на этап
  status: 'running' | 'done' | 'failed' | 'cancelled';
};

Контрольная точка как сервис

Доступ к контрольной точке текущего этапа даёт сервис Checkpoint. Его реализация привязана к конкретной паре «прогон + индекс этапа», а запись set сразу сохраняется на диск (durable).

class Checkpoint extends Context.Tag('Checkpoint')<Checkpoint, {
  get<T>(key: string): Effect.Effect<Option.Option<T>>;
  set<T>(key: string, value: T): Effect.Effect<void>;   // пишет в запись прогона
}>() {}

Идемпотентная отправка

Главный приём восстановления — сделать отправку операции идемпотентной: при возобновлении задача сперва смотрит, нет ли уже сохранённого идентификатора операции, и если есть — не отправляет запрос повторно, а сразу переходит к опросу.

const submitOnce = (req: SubmitReq) => Effect.gen(function* () {
  const cp    = yield* Checkpoint;
  const saved = yield* cp.get<string>('opId');
  if (Option.isSome(saved)) return saved.value;   // возобновление: НЕ отправляем заново

  const llm  = yield* Llm;
  const opId = yield* Effect.promise(() => llm.submit(req));
  yield* cp.set('opId', opId);                    // durable ДО начала опроса
  return opId;
});

// собранный этап опроса переиспользует submitOnce + pollUntilDone
const tcDetailsLlm: Job<{ text: string }, TcRules, Llm | Checkpoint> =
  ({ text }) => Effect.gen(function* () {
    const opId = yield* submitOnce({ system, user: text, jsonSchema });
    return yield* pollUntilDone<TcRules>(opId);
  });

Раннер: пропустить завершённое, возобновить текущее

Сам пайплайн исполняет раннер, который смотрит на запись прогона. Завершённые этапы он не перезапускает — их сохранённый выход подаётся дальше. Незавершённый этап он запускает, подставив слой Checkpoint, привязанный к этому этапу, — и задача внутри сама решает, начать заново или продолжить по контрольной точке.

const runPipeline = (run: PipelineRun, jobs: AnyJob[]) => Effect.gen(function* () {
  let input = run.input;
  for (let i = run.cursor; i < jobs.length; i++) {
    const st = run.stages[i];
    if (st.status === 'done') { input = st.output; continue; }   // не перезапускаем

    const cpLayer = makeCheckpointLayer(run.id, i);            // get/set → JsonCollection.update
    const output  = yield* jobs[i](input).pipe(Effect.provide(cpLayer));

    yield* persistStageDone(run.id, i, output);             // статус+выход+курсор (durable)
    input = output;
  }
});

Порядок записи — где это важно

Долговечность держится на двух правилах порядка. Первое: контрольную точку (opId) сохраняем до начала опроса — иначе при падении мы потеряем ссылку на уже запущенную облачную операцию. Второе: курсор продвигаем после того, как получили и сохранили выход этапа, — иначе пропустим невыполненную работу.

Честная оговоркаМежду строкой «операция отправлена» и строкой «opId сохранён» есть крошечное окно. Если процесс умрёт ровно в нём, при перезапуске мы отправим операцию повторно (потеряв первую). Сузить окно можно либо ключом идемпотентности на стороне облака (повторная отправка с тем же ключом не создаёт новую операцию), либо предварительной меткой «собираюсь отправить» с последующей выверкой. Это сознательный компромисс: без распределённого журнала транзакций окно нельзя свести строго к нулю, но можно сделать его практически безопасным.

14Сквозной пример и сценарий перезапуска

Соберём пайплайн обработки технического условия: распознать файл, разбить текст на разделы, применить результат к сущности ТУ.

const tcPipeline = [
  ocrJob,         // Job<{ fileId }, { text }>   — внутри submitOnce + pollUntilDone (OCR)
  tcDetailsLlm,   // Job<{ text }, TcRules>      — внутри submitOnce + pollUntilDone (LLM)
  applyTcRules,   // Job<TcRules, void>          — запись в доменную сущность
];

Теперь проследим сбой во время второго этапа (опрос LLM):

1. ocrJob завершился → stages[0] = done(output: { text }), cursor = 1, всё сохранено.
2. tcDetailsLlm: submitOnce отправил запрос, получил opId, записал checkpoint.opId, начал опрос.
3. ⛔ процесс упал во время опроса.
4. Перезапуск: restore() находит прогон в статусе running, зовёт runPipeline(run).
5. i=0: stages[0].status === 'done' → этап пропущен, его { text } подан дальше.
6. i=1: запускается tcDetailsLlm; submitOnce видит сохранённый opId → НЕ отправляет заново,
        сразу переходит к pollUntilDone(opId) → опрос продолжается.
7. Операция завершилась → stages[1] = done(rules), cursor = 2.
8. i=2: applyTcRules пишет результат в ТУ. Пайплайн завершён.
Здесь сошлось всёОпрос (pollUntilDone), отмена (вычисление прервалось при падении), прогресс (его читали по записи) и контрольные точки (по ним мы и продолжили). Это прямой ответ на исходный вопрос: «продолжить опрос либо сразу перейти к нему, если предыдущий этап завершён».

16Открытые вопросы и риски

  • Порог входа. Effect — мощная, но непривычная модель; команде нужно освоить хотя бы основания из Части I. Это инвестиция, оправданная только если механизмы (композиция, отмена, повторы, типизированные ошибки) реально используются — а у нас используются.
  • Мост Nest ↔ Effect. Нужно аккуратно описать, как Nest-провайдеры превращаются в Layer и где находится единая точка запуска/восстановления (вероятно, сервис-раннер с OnApplicationBootstrap).
  • Гранулярность контрольных точек. Что считать атомарным шагом: чем мельче точки, тем надёжнее возобновление, но тем чаще запись на диск.
  • Политика повторов. Где уместен retry с нарастающей паузой (сетевые сбои), а где — нет (бизнес-ошибка, которую повтор не исправит).
  • Реестр Job и восстановление. Как сопоставлять сохранённый прогон с кодом пайплайна (по имени), и что делать, если набор этапов изменился между версиями.
  • Окно идемпотентности отправки (см. раздел 13) — выбрать конкретную стратегию для облачных операций Yandex.
