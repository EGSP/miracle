В проекте бывшие «воркеры» (OCR, LLM-разбор ТУ, анализ заявки, обозначение) переписаны на единый durable-движок задач. Единица работы — Job: это не «запущенный процесс», а описание, которое движок исполняет, сохраняя прогресс. Если процесс упадёт посреди долгой облачной операции, после перезапуска джоб продолжится с того же места. Ниже — как это устроено и как прочитать состояние с фронта.

1Что это и из чего состоит

Движок живёт в back-nest/src/jobs/ и состоит из нескольких частей:

ЧастьРоль
job.tsleaf(id, fn) — листовой джоб (делает работу); составной строится комбинаторами. Job — описание, не Effect.
combinators.tsandThen (цепочка), named (имя пайплайна).
context.tsEffect-теги Memo (контрольная точка) и Progress (прогресс) — их даёт раннер.
runner.tsРекурсивно исполняет дерево, пишет состояние, пропускает завершённое, возобновляет незавершённое.
registry.tsРеестр корневых джобов по id — нужен для восстановления после перезапуска.
job-runtime.service.ts@Global сервис: start / applyById / cancel + восстановление прогонов на старте.
JobRun (в @miracle/types)Запись об исполнении (дерево), коллекция jobRuns.

2Как определить джоб

Джоб собирается из листьев. Лист — это leaf(id, fn), где fn принимает вход и возвращает Effect. Несколько листьев соединяются в цепочку через pipe + andThen, а named даёт имя всему пайплайну. Пример — реальный tc-extract (разбор ТУ):

// ЛИСТ 1: подготовить текст → отправить в LLM → опросить до готовности.
// Зависимости (yandex, deps.tc, …) приходят замыканием — см. раздел 3.
const tcDetailsLlm = leaf('tc-details-llm', (input: { tcId: string }) =>
  Effect.gen(function* () {
    const text = yield* getTcText(input.tcId);

    // submitOnce: при возобновлении берёт opId из memo и НЕ шлёт повторно;
    // finalPrompt кладётся в memo ДО отправки — чтобы показать превью даже при сбое.
    const opId = yield* submitOnce(
      () => deps.yandex.submitCompletion({ messages: [ /* … */ ], jsonSchema }),
      { finalPrompt: { system: SYSTEM_PROMPT, user: text } },
    );

    const result = yield* pollUntilDone(() => deps.yandex.pollCompletionJson(opId, schema));
    return { tcId: input.tcId, sections: result.sections }; // ВЫХОД листа
  }),
);

// ЛИСТ 2 (apply): записать результат в доменную сущность.
const tcApply = leaf('tc-details-apply', (input) =>
  Effect.gen(function* () { /* deps.tc.replace(input.tcId, { rules, … }) */ }));

// СОСТАВНОЙ ДЖОБ: цепочка листьев. Типы стыков проверяет компилятор.
const tcExtract = tcDetailsLlm.pipe(andThen(tcApply), named('tc-extract'));
Почему лист и apply разделены«Получить результат» (дорогая облачная операция) и «применить результат» (дешёвая запись) — разные шаги. Это позволяет повторно применить результат (apply-worker-data), не запуская LLM заново.

3Как джоб получает зависимости (фабрики)

Джоб не импортирует сервисы напрямую. Их замыкает фабрика — обычный Nest-провайдер, которому сервисы внедряются конструктором. Он строит джобы и регистрирует их в реестре. Это и есть «DI через фабрики»: вся проводка зависимостей — здесь, а сам джоб остаётся чистым описанием.

// technical-conditions/tc-jobs.service.ts
@Injectable()
export class TcJobs implements OnModuleInit {
  readonly tcExtract: AnyJob;

  constructor(tc: TechnicalConditionsService, filesContent: FilesContentService, yandex: YandexService) {
    // createTcJobs замыкает сервисы внутри листьев (deps.tc, deps.yandex, …)
    this.tcExtract = createTcJobs({ tc, filesContent, yandex }).tcExtract;
  }

  onModuleInit() { registerJob(this.tcExtract); } // в реестр — для восстановления после рестарта
}
Почему так, а не Effect-слоиСервисы NestJS приходят в листья замыканием, поэтому раннеру не нужен Effect-`Layer` с доменными зависимостями: к моменту запуска у эффекта нет требований, кроме Memo/Progress, которые подаёт сам раннер. Меньше связок, нет циклов между модулем джобов и доменами.

4Как в джоб попадают данные (запуск)

Данные попадают через вход, который передаётся в JobRuntimeService.start(job, input). Обычно это делает контроллер или доменный сервис. start создаёт корневую запись прогона (JobRun, статус queued) и форкает исполнение в фоне, сразу вернув запись с её id.

// technical-conditions/technical-conditions.controller.ts
@Post(':id/extract-details')
@HttpCode(202)
async extractDetails(@Param('id') id: string) {
  const tc = this.tc.getByIdOrThrow(id);
  if (!tc.fileId) throw new BadRequestException('TC не имеет PDF-файла');

  const run = await this.runtime.start(this.tcJobs.tcExtract, { tcId: id }); // ← вход джоба
  return { runId: run.id }; // id прогона — клиенту для слежения
}

Другой пример — извлечение содержимого: при VISUAL-файле ExtractionService создаёт запись контента и стартует подходящий scan-джоб (ocr / llm-vision / llm-vision-tc) с входом { fileId, fileContentId }.

5Как данные переходят между этапами

Правило одно: возвращаемое значение листа становится входом следующего листа в цепочке. Раннер берёт output завершённого шага и подаёт его в input следующего. Поэтому в выход кладут всё, что нужно дальше.

// tcDetailsLlm возвращает { tcId, sections } →
// именно это приходит во вход tcApply (типы стыка проверяет компилятор).
tcDetailsLlm.pipe(andThen(tcApply))
//  Job<{tcId}, {tcId,sections}>  →  Job<{tcId,sections}, void>
ГраблиКорневой input идёт только в первый лист. Если apply-листу нужен, например, tcId — его кладут в выход первого листа (как в примере: { tcId, sections }), а не «достают» из корневого входа.

Внутри листа есть два дополнительных канала, которые даёт раннер: Memo — сохранить контрольную точку для возобновления (например opId, finalPrompt); Progress — сообщить о ходе работы. Оба пишут в запись прогона немедленно (durable).

6Что сохраняется: запись JobRun

Состояние исполнения хранится в коллекции jobRuns как единое рекурсивное дерево JobRun: у листа — memo/output, у составного — steps (дети) и cursor.

type JobStatus = 'queued' | 'running' | 'succeeded' | 'failed' | 'cancelled';

type JobRun = {
  id: string; job: JobId; status: JobStatus;
  input?: unknown; output?: unknown; error?: string;
  progress?: { phase: string; pct?: number };
  memo?: Record<string, unknown>;   // ЛИСТ: { opId, finalPrompt, … }
  cursor?: number;                   // СОСТАВНОЙ: индекс текущего ребёнка
  steps?: JobRun[];                  // СОСТАВНОЙ: вложенные прогоны
};

Пример: tc-extract упал во время опроса LLM. В базе лежит:

{
  "id": "run_1", "job": "tc-extract", "status": "running", "cursor": 0,
  "input": { "tcId": "tc_42" },
  "steps": [
    { "job": "tc-details-llm", "status": "running",
      "memo": { "opId": "op_abc", "finalPrompt": { "system": "…", "user": "…" } } },
    { "job": "tc-details-apply", "status": "queued" }
  ]
}

7Жизненный цикл, восстановление, повтор

queued → running → succeeded · (или failed / cancelled)

  • Восстановление. На старте приложения JobRuntimeService находит прогоны со статусом running/queued, по job берёт определение из реестра и заново запускает раннер. Завершённые шаги пропускаются (их выход переиспользуется), незавершённый tc-details-llm по memo.opId продолжает опрос — без повторной отправки.
  • Повторное применение (applyById, эндпоинт apply-worker-data): последний шаг сбрасывается в queued, прогон гоняется снова — LLM-шаг пропускается (уже succeeded), выполняется только apply.
  • Отмена (cancel): прерывает волокно и помечает прогон cancelled (цикл опроса прерывается на Effect.sleep).

8Прогресс

Прогресс считается по дереву JobRun. В jobs/progress.ts есть готовые функции:

import { progressStages, overallProgress } from '../jobs/progress.js';

overallProgress(run);       // общий прогресс 0..100
progressStages(run, 1);     // [{ name, weight, progress }] — прямые дети корня
// weight в сумме = 100 (доля этапа); progress в сумме = общий прогресс.

Эти же функции можно повторить на фронте по полученному дереву, либо завести серверный эндпоинт, отдающий уже посчитанные этапы.

9Чтение на фронтенде

Прогоны отдаёт домен workers (исторический путь /workers). Это брейкендж: раньше там был старый WorkerData, теперь — JobRun (см. BREAKING-CHANGES.md).

ЭндпоинтНазначение
GET /workers?status=&sort=Список прогонов JobRun (фильтр по статусу, сортировка по дате).
GET /workers/:id/preview-promptСохранённый промпт из memo.finalPrompt LLM-узла.
POST /workers/:id/apply-worker-dataПовторно применить результат завершённого прогона.
DELETE /workers/:idУдалить прогон (нельзя для running).

Запустившие джоб эндпоинты (extract-details, analyse-details, …) возвращают { runId }. Клиент по нему отслеживает прогон: опрашивает список (пока нет отдельного GET /workers/:id — его легко добавить) и находит запись по id.

Отрисовка по статусу

Статус — размеченное объединение, поэтому на фронте удобно ветвление по нему (ср. с лекцией про отзывчивый React):

function JobView({ run }: { run: JobRun }) {
  switch (run.status) {
    case 'queued':
    case 'running':   return <Progress value={overall(run)} />;
    case 'failed':    return <ErrorView message={run.error} />;
    case 'cancelled': return <Note>Отменено</Note>;
    case 'succeeded': return <Done />;
  }
}

// прогресс по дереву — повтор серверной логики progressStages
function overall(node: JobRun): number {
  if (node.status === 'succeeded') return 100;
  if (node.status === 'failed' || node.status === 'cancelled') return 0;
  if (node.steps?.length) return node.steps.reduce((s, c) => s + overall(c), 0) / node.steps.length;
  return node.status === 'running' ? (node.progress?.pct ?? 0) : 0;
}

Опрос пока идёт

// перезапрашивать список, пока есть running-прогоны (или для конкретного runId)
useQuery({ queryKey: ['jobRuns'], queryFn: fetchWorkers,
  refetchInterval: (data) => data?.some(r => r.status === 'running') ? 2000 : false });

10Как добавить новый джоб (чеклист)

  1. Написать листья: leaf('my:step', (input) => Effect.gen(…)); для облачных операций — submitOnce + pollUntilDone.
  2. Собрать пайплайн: step1.pipe(andThen(step2), named('my-job')). Выход шага = вход следующего.
  3. Сделать фабрику-провайдер (@Injectable), замкнуть сервисы, registerJob(...) в onModuleInit.
  4. Запускать через JobRuntimeService.start(job, input) из контроллера/сервиса; вернуть клиенту { runId }.
  5. Долгие операции: opId сохранять в memo ДО опроса; промпт — в memo.finalPrompt для превью.
  6. На фронте: отслеживать по /workers, ветвить по status, прогресс — по дереву steps.
