Отзывчивый React-интерфейс: ре-рендеры, передача данных и отображение состояний

Ориентир — React 19.2 и Zustand 5. Только клиентская часть, без серверных эффектов.

«Отзывчивый» интерфейс — это интерфейс, который не замирает: поле ввода реагирует на каждое нажатие, кнопка показывает, что запрос идёт, а тяжёлый список не блокирует остальную страницу. Чтобы добиться этого без хаоса в коде, нужно понимать две вещи: когда React перерисовывает компоненты и как передавать данные так, чтобы перерисовок было ровно столько, сколько нужно. С этого и начнём, а затем перейдём к компонентам, которые честно отображают своё состояние — загрузку, ошибку, пустоту, успех.

1Как React решает, что перерисовать

Базовое правило простое: когда у компонента меняется состояние (англ. state) или входные свойства (англ. props), React заново вызывает его функцию и функции всех его потомков. «Перерисовка» (англ. re-render) здесь — это не обновление страницы в браузере, а повторный вызов функции-компонента, чтобы вычислить, как должно выглядеть дерево. Реальные изменения в DOM React внесёт только там, где результат отличается.

Важное следствие, которое часто упускают: родитель перерисовывает детей по факту своей перерисовки, даже если их собственные props не менялись. Сравнение props спасает не само по себе, а только если компонент обёрнут в memo.

function Parent() {
  const [n, setN] = useState(0);
  return (
    <div onClick={() => setN(n + 1)}>
      <Expensive />   // перерисовывается на каждый клик, хотя props не менялись
    </div>
  );
}
Почему это такReact не знает заранее, зависит ли Expensive от чего-то изменившегося. Дешевле перерисовать (вызвать функцию) и сравнить результат, чем доказывать ненужность. Наша задача — расставить подсказки там, где перерисовка действительно дорогая, а не везде подряд.

2Как уменьшить лишние ре-рендеры

Есть три приёма, и применять их стоит именно в таком порядке — от самого дешёвого по сложности к самому затратному.

2.1. Колокация: держите состояние как можно ниже

Если состояние нужно одному небольшому поддереву, опустите его туда. Тогда перерисовываться будет только это поддерево, а не вся страница. Частая ошибка — хранить «всё подряд» в самом верхнем компоненте.

2.2. Композиция: передавайте содержимое через children

Если стейт меняется в обёртке, но дорогое содержимое от него не зависит — вынесите содержимое в children. Элемент, созданный снаружи, не пересоздаётся при перерисовке обёртки.

Лишняя перерисовка

function Panel() {
  const [open, setOpen] = useState(0);
  return <div><Expensive /></div>;
}

Содержимое снаружи

function Panel({ children }) {
  const [open, setOpen] = useState(0);
  return <div>{children}</div>;
}
<Panel><Expensive /></Panel> // не ре-рендерится

2.3. Мемоизация: memo, useMemo, useCallback

Когда первые два приёма исчерпаны, помогает мемоизация. memo пропускает перерисовку компонента, если его props не изменились по ссылке. useMemo кэширует результат тяжёлого вычисления, useCallback — стабильную ссылку на функцию (нужно, когда функцию передаём в memo-компонент или в зависимости хука).

const Row = memo(function Row({ item, onPick }) { /* ... */ });

function List({ items }) {
  const onPick = useCallback((id) => /* ... */, []);      // стабильная ссылка
  const sorted = useMemo(() => [...items].sort(byName), [items]); // кэш вычисления
  return sorted.map((it) => <Row key={it.id} item={it} onPick={onPick} />);
}
Когда НЕ нужноНе оборачивайте всё подряд. Мемоизация сама по себе стоит памяти и усложняет чтение; для маленьких деревьев перерисовка дешевле, чем сравнение. Сначала — колокация и композиция (раздел 2.1–2.2), и лишь для доказанно дорогих участков — memo. «Преждевременная мемоизация» — частый источник сложного и хрупкого кода.

3Куда положить состояние: props, контекст, хранилище

Это центральный вопрос баланса «скорость отрисовки против сложности кода». Есть три способа доставить данные компоненту, и у каждого своя цена.

3.1. Свойства (props) — выбор по умолчанию

Передача через props — самая простая, явная и быстрая: видно, откуда пришли данные, и легко тестировать. Единственная проблема появляется, когда данные нужно «протащить» через много уровней (англ. prop drilling) — тогда промежуточные компоненты обрастают свойствами, которые им самим не нужны.

3.2. Контекст (context) — для «окружения», а не для частых изменений

Контекст устраняет протаскивание: значение объявляется наверху и доступно любому потомку. Он хорошо подходит для редко меняющегося «окружения» — тема оформления, текущий пользователь, язык, общие зависимости.

Главная ловушка контекстаУ контекста нет выборочной подписки: при изменении значения перерисовываются все потребители, даже те, кто читает лишь его часть. Поэтому в контекст не кладут часто меняющееся состояние (позицию курсора, ввод, прогресс). Если значение всё же меняется — мемоизируйте его и при необходимости разделяйте на два контекста: отдельно данные, отдельно функции их изменения.
// объект-значение пересоздаётся каждый рендер → все потребители ре-рендерятся
<ThemeContext.Provider value={{ theme, setTheme }}>

// мемоизируем; функции стабильны, данные отдельно от действий
const value = useMemo(() => ({ theme }), [theme]);
<ThemeContext.Provider value={value}>

3.3. Хранилище (store) — для частого и «сквозного» состояния

Когда состояние меняется часто, нужно многим далеко отстоящим компонентам, или это «сквозная» доменная сущность (корзина, сессия, открытый диалог) — выгоднее внешнее хранилище. В проекте это Zustand. Его ключевое отличие от контекста — выборочная подписка через селектор: компонент перерисовывается только когда меняется именно тот срез, который он читает.

const useCartStore = create<CartState>((set) => ({
  items: [],
  addItem: (it) => set((s) => ({ items: [...s.items, it] })),
}));

// подписка на срез: ре-рендер только при изменении количества
const count = useCartStore((s) => s.items.length);
Правило стабильности селектора (из практики проекта)Zustand построен на useSyncExternalStore, который сравнивает результат селектора по ссылке. Если селектор возвращает новый объект или функцию на каждый рендер, React считает значение изменившимся — это лишние ре-рендеры, а иногда и предупреждение о «бесконечном» обновлении. Возвращайте примитивы отдельными вызовами либо используйте useShallow для поверхностного сравнения.

Плохо: новый объект

const { items, addItem } =
  useStore((s) => ({
    items: s.items,
    addItem: s.addItem,
  })); // новая ссылка каждый рендер

Хорошо: примитивы или useShallow

import { useShallow } from 'zustand/react/shallow';

const items   = useStore((s) => s.items);
const addItem = useStore((s) => s.addItem);
// или одним селектором с поверхностным сравнением:
const { items, addItem } =
  useStore(useShallow((s) => ({ items: s.items, addItem: s.addItem })));

Не тащите всё в глобальный store «на всякий случай»: глобальное состояние, которое могло бы быть локальным, — это и лишние ре-рендеры, и труднее отслеживаемые зависимости.

4Срочные и несрочные обновления: useTransition

Иногда одно действие пользователя порождает два обновления разной срочности. Набор текста в поле — срочное: поле обязано реагировать мгновенно. Перестроение тяжёлого списка по этому тексту — несрочное: его не страшно отрисовать чуть позже. Если делать оба синхронно, ввод начнёт «заедать», потому что React будет занят тяжёлым списком.

Хук useTransition помечает обновление как несрочное (переход, англ. transition). React сначала отрисует срочное (поле), сохранит отзывчивость, а тяжёлое посчитает в фоне и при необходимости прервёт, если придёт новый ввод.

const [query, setQuery] = useState('');
const [results, setResults] = useState([]);
const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                      // срочно: поле ввода
  startTransition(() => {
    setResults(filterHugeList(e.target.value));    // несрочно: тяжёлый список
  });
}

return (
  <>
    <input value={query} onChange={onChange} />
    {isPending && <Spinner />}            // честно показываем: список догоняет
    <Results data={results} />
  </>
);
React 19В переход можно завернуть и асинхронное действие — тогда isPending остаётся истинным на всё время операции. Это основа «действий» (англ. Actions), к которым придём в разделе 8.

5Отложенное значение: useDeferredValue

Иногда мы не управляем местом, где запускается обновление (значение приходит сверху как prop). Тогда вместо того чтобы помечать обновление, можно пометить значение как «допустимо отстающее». useDeferredValue возвращает версию значения, которая обновится с небольшим запозданием, пока React занят срочным.

function Results({ query }) {
  const deferred = useDeferredValue(query);          // «отстающая» копия
  const list = useMemo(() => filterHugeList(deferred), [deferred]);
  const stale = deferred !== query;                  // показываем, что данные устаревают
  return <div style={{ opacity: stale ? 0.6 : 1 }}><Rows data={list} /></div>;
}
useTransition или useDeferredValueПравило простое: если вы сами вызываете обновление — оборачивайте его в startTransition. Если значение приходит извне и вы лишь реагируете — используйте useDeferredValue. Оба держат интерфейс отзывчивым; разница лишь в том, на чьей стороне источник изменения.

6Состояние как размеченное объединение

Компонент, загружающий данные, имеет несколько взаимоисключающих состояний: ожидание, успех, ошибка, иногда «пусто». Частая ошибка — описывать их набором булевых флагов (isLoading, isError, data). Такой «булев суп» допускает невозможные сочетания (isLoading && isError) и легко приводит к ошибкам по невнимательности.

Надёжнее описать состояние размеченным объединением (англ. discriminated union): одно поле-метка status, и для каждого значения метки — только релевантные данные. Невозможные состояния становятся невыразимыми, а компилятор заставляет обработать все случаи.

Булев суп

type State = {
  isLoading: boolean;
  isError: boolean;
  data?: User;
  error?: Error;
}; // допускает невозможное

Размеченное объединение

type Async<T> =
  | { status: 'idle' }
  | { status: 'pending' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

7Декларативные загрузка и ошибка: Suspense и границы

Размеченное объединение хорошо, когда состоянием управляем мы сами. Но часть состояний React умеет отображать декларативно, без ручных флагов. Suspense показывает запасной интерфейс (англ. fallback), пока данные «приостановлены», а граница ошибок (англ. error boundary) перехватывает сбой и показывает запасной экран. В React 19 хук use позволяет прямо «прочитать» промис, приостановив компонент до его разрешения.

function Profile({ userPromise }) {
  const user = use(userPromise);   // приостанавливает, пока промис не разрешится
  return <h1>{user.name}</h1>;
}

<ErrorBoundary fallback={<ErrorView />}>   // перехват ошибки
  <Suspense fallback={<Skeleton />}>       // заглушка на время загрузки
    <Profile userPromise={userPromise} />
  </Suspense>
</ErrorBoundary>
Почему это удобноСостояния «загрузка» и «ошибка» вынесены из компонента в его окружение. Сам Profile пишется так, будто данные уже есть, — меньше веток, меньше шансов забыть случай. Состоянием же «успех/пусто» по-прежнему управляем явно (раздел 6).
ЗамечаниеГраница ошибок в React реализуется компонентом-классом (или готовой из библиотеки) — это единственное место, где класс ещё нужен. Достаточно одной такой границы на крупный участок интерфейса.

8Действия и формы: useActionState, useFormStatus, useOptimistic

Отправка формы или мутация — это тоже состояние: «отправляется», «успех», «ошибка». React 19 даёт под это связку хуков, чтобы не собирать её вручную из useState и try/catch.

useActionState — состояние действия

Принимает асинхронную функцию-действие и начальное состояние, возвращает текущее состояние, обёртку для формы и признак выполнения isPending.

const [state, formAction, isPending] = useActionState(
  async (prev, formData) => {
    try { await saveProfile(formData); return { ok: true }; }
    catch (e) { return { ok: false, error: message(e) }; }
  },
  { ok: false },
);

return (
  <form action={formAction}>
    <input name="name" />
    {state.error && <p className="err">{state.error}</p>}
    <SubmitButton />
  </form>
);

useFormStatus — состояние ближайшей формы

Позволяет вложенной кнопке узнать, идёт ли отправка родительской формы, не прокидывая признак через props.

import { useFormStatus } from 'react-dom';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Сохраняю…' : 'Сохранить'}</button>;
}

useOptimistic — оптимистичный интерфейс

Показывает результат действия сразу, ещё до ответа сервера, а при ошибке React сам откатит оптимистичное значение к реальному. Это резко повышает ощущение отзывчивости.

const [optimisticTodos, addOptimistic] = useOptimistic(
  todos,
  (current, draft) => [...current, { ...draft, sending: true }],
);

async function submit(formData) {
  const draft = { text: formData.get('text') };
  addOptimistic(draft);          // мгновенно дорисовали «отправляется»
  await saveTodo(draft);          // при ошибке оптимистичный элемент откатится
}

9Переиспользуемый компонент-переключатель состояний

Когда состоянием управляем сами (раздел 6), удобно иметь один компонент, который по метке status выбирает, что показать. Тогда каждая страница не повторяет одинаковые ветки «загрузка/ошибка/пусто».

function Async<T>({ state, children, empty }: {
  state: Async<T>;
  children: (data: T) => React.ReactNode;
  empty?: React.ReactNode;
}) {
  switch (state.status) {
    case 'idle':
    case 'pending': return <Skeleton />;
    case 'error':   return <ErrorView error={state.error} />;
    case 'success':
      return isEmpty(state.data) ? (empty ?? <Empty />) : children(state.data);
  }
}

// применение — чтение остаётся коротким и без веток
<Async state={users}>
  {(list) => <UserTable rows={list} />}
</Async>
Что мы выигралиВетвление состояний собрано в одном месте и описано через размеченное объединение, поэтому компилятор проверит, что обработаны все случаи. Страница же читается декларативно: «вот данные — вот таблица», без переплетения с загрузкой и ошибками.
