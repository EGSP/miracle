До этого момента данные miracle лежали в JSON-файлах: каждая коллекция — это массив объектов, и форму объекта можно было менять как угодно, прямо в коде. PostgreSQL устроен иначе: форма данных фиксируется заранее и охраняется самой базой. Из-за этого появляется новая задача — как менять эту форму, не теряя то, что уже накоплено. Инструмент для этого и называется миграциями. Эта лекция объясняет их с самого основания — не предполагая, что вы раньше писали SQL.

1Что такое таблица, строка и схема

Начнём с того, что вы уже знаете. В текущем проекте коллекция users — это файл с массивом объектов:

// users.json — то, что было в lowdb
{ items: [
  { id: "u1", login: "anna", role: "admin" },
  { id: "u2", login: "egor", role: "user" },
]}

В реляционной базе (PostgreSQL — одна из них) это превращается в таблицу. Соответствие почти дословное:

Мир JSON / lowdbМир SQL-базы
файл-коллекция users.jsonтаблица users
один объект в массивестрока (row)
поле объекта loginколонка (column)
тип поля в TypeScriptтип колонки в базе (TEXT, INTEGER…)

Ключевое отличие — в одном слове: фиксированность. В JSON один объект мог иметь поле phone, а соседний — нет, и никто не возражал. В SQL-таблице набор колонок и их типы заданы заранее и одинаковы для всех строк. Этот заранее заданный «чертёж» таблиц — какие есть таблицы, какие у них колонки, каких типов, какие связи между ними — и называется схемой (schema).

Зачем база себя так ограничиваетФиксированная форма — не каприз, а источник надёжности и скорости. База гарантирует, что в колонке email всегда строка, что у заказа всегда есть существующий автор, что двух пользователей с одним email не появится. Эти проверки делает сама база, а не ваш код — поэтому им можно доверять.

2Почему форму базы нельзя поменять «просто так»

Раз форма зафиксирована и охраняется, изменить её — это отдельное действие. В JSON, чтобы добавить телефон пользователю, вы просто дописывали поле в тип и в объект. В SQL так нельзя: таблица users уже существует в базе с конкретным набором колонок, и в ней, возможно, уже лежат строки. Чтобы появилась колонка phone, базе нужно отдать явную команду.

Команды, меняющие структуру (а не данные), пишутся на языке SQL и выглядят так:

ALTER TABLE users ADD COLUMN phone TEXT;   -- добавить колонку
ALTER TABLE users DROP COLUMN phone;       -- удалить колонку
CREATE TABLE orders ( ... );                -- создать новую таблицу

Запоминать этот SQL вам не придётся — его за вас напишет Prisma (об этом вся остальная лекция). Но важно понять идею: переход базы из одной формы в другую — это последовательность таких команд. И тут возникает настоящая проблема, которой не было в мире JSON.

Главная сложностьМенять форму нужно так, чтобы не потерять уже накопленные данные. Удалить колонку — значит стереть её значения во всех строках. Сменить тип — значит как-то преобразовать существующие значения. Если в базе сто тысяч реальных записей, ошибка в таком изменении необратима. Именно ради безопасного изменения формы и существует весь механизм миграций.

3Миграция — это записанный шаг изменения

Можно было бы менять форму, набирая SQL-команды руками прямо в базе. Так и делали раньше — и так до сих пор делают новички, наживая проблемы. Беда в том, что такое изменение нигде не записано: на вашей машине база уже новая, а у коллеги и на сервере — старая, и привести их к одному виду нечем, кроме памяти.

Миграция решает это просто: каждый шаг изменения структуры записывается в файл. Файл — это и есть те самые SQL-команды, но сохранённые на диск, в репозиторий, с номером по порядку.

// так выглядит каталог миграций на диске
prisma/migrations/
  20260601_init/            -- шаг 1: создать все таблицы
    migration.sql
  20260615_add_user_phone/  -- шаг 2: добавить колонку phone
    migration.sql
  20260620_orders_status/   -- шаг 3: ...
    migration.sql

Теперь «привести любую базу к нужной форме» = «выполнить по порядку все файлы миграций, которых в ней ещё нет». Это работает одинаково на вашей машине, у коллеги и на боевом сервере. История изменений структуры лежит в git рядом с кодом.

Запомните формулировкуМиграция — это один зафиксированный шаг превращения схемы из состояния «до» в состояние «после», сохранённый как файл с SQL. Набор миграций по порядку — это полная история того, как база дошла до текущей формы.

4schema.prisma — единственный источник правды

Писать SQL руками всё же не хочется. Здесь и вступает Prisma. Вы описываете желаемую форму базы в одном файле — schema.prisma — на удобном декларативном языке:

model User {
  id        String   @id @default(uuid())
  login     String
  role      UserRole
  phone     String?            // ? — колонка необязательная (может быть пустой)
  createdAt DateTime @default(now())
}

Дальше Prisma берёт на себя всю чёрную работу. Её инструмент сравнивает два состояния — что написано в схеме и что сейчас в базе — вычисляет разницу и сам генерирует нужный SQL. Вы декларируете «как должно быть», Prisma вычисляет «что для этого выполнить».

schema.prisma (как хочу)  →  Prisma сравнивает с базой  →  вычисляет разницу  →  SQL-команды (что выполнить)

Из этой картины растут оба режима работы, между которыми и предстоит выбирать. Разница между ними — что Prisma делает с этим вычисленным SQL: выполнить молча и забыть, или сохранить в файл-миграцию.

5Режим без истории: db push

Первый режим — самый простой. Команда prisma db push вычисляет разницу и сразу применяет её к базе. Файл миграции при этом не создаётся — изменение нигде не записывается, просто база приводится к виду схемы.

# поменял schema.prisma → выполнил одну команду
npm run prisma:push

Это идеальный режим, пока в базе нет ценных данных — то есть ровно текущая ситуация miracle. Меняешь схему как угодно часто, давишь push, работаешь дальше. Никакой возни с файлами. Если база запуталась — сбрасываешь её целиком:

npm run prisma:reset   # стереть всё, создать заново по схеме + наполнить тестовыми данными
Почему без истории — это нормально на стартеПока данные тестовые, история изменений не нужна: их не жалко потерять, а воспроизводить «как именно мы пришли к этой схеме» незачем — схема ещё скачет каждый день. Запись каждого шага в файл на этой стадии только мешала бы. Поэтому: пустая база → db push, и никаких миграций.

6Режим с историей: migrate

Второй режим включают, когда в базе появляются данные, которые нельзя потерять (первый боевой сервер, демо-стенд с введёнными вручную записями). Команда prisma migrate dev делает то же сравнение, но вычисленный SQL сохраняет в новый файл-миграцию и только потом применяет.

# поменял схему → создать и применить миграцию с понятным именем
npm run prisma:migrate -- --name add_user_phone

Что появляется в проекте при этом режиме:

  • Каталог prisma/migrations/ — те самые пронумерованные файлы с SQL. Они едут в git вместе с кодом.
  • Служебная таблица _prisma_migrations — Prisma создаёт её прямо в базе и записывает туда, какие миграции уже применены. Так база «помнит», на каком шаге истории она находится, и не применяет один файл дважды.
Как база понимает, что ей делатьПри запуске Prisma смотрит в таблицу _prisma_migrations, видит список уже применённых файлов, сравнивает с каталогом migrations/ и применяет только недостающие. Поэтому одну и ту же команду можно запускать сколько угодно раз — лишнего она не сделает.

7Жизненный цикл: dev, миграции, production

Сложим оба режима в одну временную линию — как проект проходит её в реальности.

  1. Ранняя разработка (мы здесь). Данных нет. Живём на db push и reset. Каталога migrations/ в проекте ещё нет.
  2. Схема устоялась / готовимся к первому деплою. Один раз выполняем migrate dev --name init — Prisma создаёт первый файл-миграцию, описывающий всю текущую схему целиком («создать такие-то таблицы»). С этого момента проект — «на миграциях».
  3. Дальнейшая разработка. Каждое изменение схемы оформляем как новую миграцию: migrate dev --name .... Файлы копятся в git.
  4. Выкатка на боевой сервер. Там не генерируют миграции. Там выполняют только готовые: prisma migrate deploy — эта команда берёт файлы из репозитория и применяет недостающие к боевой базе, не задавая вопросов.
локально: migrate dev (придумали и записали шаг)   →  git  →   на сервере: migrate deploy (применили готовый шаг)
Два правила, которые экономят нервыmigrate dev — только на машине разработчика (он умеет генерировать и может задавать вопросы). На production — только migrate deploy. И: на одной базе нельзя смешивать db push с migrate — выбрав миграции, про db push для этой базы забывают.

8Анатомия файла миграции

Раз миграция — это файл с SQL, посмотрим, что внутри. Бояться не нужно: язык читается почти по-английски. Вот начало реальной миграции «создать таблицу users»:

CREATE TABLE "users" (
    "id"        TEXT NOT NULL,            -- колонка id, строка, обязательная
    "login"     TEXT NOT NULL,
    "phone"     TEXT,                     -- без NOT NULL — значит, может быть пустой
    "createdAt" TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "users_pkey" PRIMARY KEY ("id")   -- id — главный ключ, уникален
);

Читается прямо: «создать таблицу users с колонками id (текст, обязательна), login, phone (необязательна), createdAt (время, по умолчанию — текущий момент); главный ключ — id». Этот файл сгенерировала Prisma сама из вашей модели User. В 95% случаев вы его даже не открываете — Prisma всё сделала правильно.

Остальные 5% — когда заглянуть в файл и поправить его руками всё-таки нужно. Им посвящены следующие два раздела: это и есть то место, где у новичков рождается страх перед миграциями, и где этот страх снимается.

9Когда Prisma не угадывает намерение

Prisma сравнивает схему с базой по фактическому различию, но она не читает ваши мысли. Классический пример — переименование колонки. Вы переименовали в схеме login в username. Для Prisma это выглядит как «колонка login исчезла, колонка username появилась», и она честно сгенерирует:

Что сгенерирует Prisma

ALTER TABLE users
  DROP COLUMN "login";     -- ❌ удалит все логины
ALTER TABLE users
  ADD COLUMN "username" TEXT; -- создаст пустую колонку

Что вы имели в виду

ALTER TABLE users
  RENAME COLUMN "login"
  TO "username";          -- ✓ данные сохранены

Намерение было «переименовать, сохранив значения», а сгенерированный SQL их сотрёт. Решение — перехватить файл до применения. Для этого есть ключ --create-only: он говорит Prisma «сгенерируй файл миграции, но не применяй его»:

# 1. Prisma создаёт файл, но НЕ трогает базу
npm run prisma:migrate -- --create-only --name rename_login

# 2. открываешь migration.sql и заменяешь DROP/ADD на RENAME (вручную)

# 3. теперь применяешь отредактированный файл
npm run prisma:migrate
Вот и весь секрет «ручных миграций»«Ручная миграция» — это не отдельная сложная технология и не обход Prisma. Это тот же самый файл миграции, который вы открыли и поправили перед применением, потому что лучше Prisma знаете намерение. Деления на «призмовские» и «ручные» миграции нет — есть один файл, иногда отредактированный человеком.

10Сохранить данные: expand → migrate → contract

Вторая ситуация, где нужна ручная правка, — когда новое требование к структуре противоречит уже лежащим данным. Пример: вы добавляете обязательную (NOT NULL) колонку status в таблицу с тысячей существующих заказов. Нельзя просто объявить колонку обязательной — у тысячи старых строк значения нет, и база отвергнет такое изменение.

Безопасный приём разбивает изменение на три шага. У него есть устоявшееся название — expand → migrate → contract (расширить → перенести → сузить):

-- ШАГ 1 (expand): добавить колонку как НЕобязательную — это всегда безопасно
ALTER TABLE orders ADD COLUMN "status" TEXT;

-- ШАГ 2 (migrate): заполнить значение у всех старых строк
UPDATE orders SET "status" = 'draft' WHERE "status" IS NULL;

-- ШАГ 3 (contract): теперь, когда пустых нет, сделать колонку обязательной
ALTER TABLE orders ALTER COLUMN "status" SET NOT NULL;

Команда UPDATE ... SET в шаге 2 — это и есть «перенос/заполнение данных» (backfill). Она не меняет структуру, она проставляет значения. Такие шаги Prisma за вас не придумает — их дописывают руками в файл миграции через тот же --create-only.

Золотое правило data-preserving миграцийНикогда не соединяйте «перенести данные» и «удалить старое» в одной миграции. Сначала миграция, которая добавляет новое и переносит. Проверяете, что данные на месте. И только потом отдельной миграцией удаляете старое. Так у вас всегда есть точка, в которой ничего ещё не потеряно.

11Почему миграции не редактируют и не «откатывают»

Два вопроса, которые возникают у каждого новичка.

«Я ошибся в применённой миграции — поправлю файл»

Нельзя. Как только миграция применена (к вашей базе, к базе коллеги, на сервере), она считается неизменяемой. Prisma запоминает её «отпечаток» в таблице _prisma_migrations; если потом изменить файл, отпечаток разойдётся и Prisma поднимет тревогу о рассинхроне. Правильно — сделать новую миграцию, которая исправляет предыдущую. История идёт только вперёд и ничего не переписывает задним числом — как коммиты в git.

«Как откатить миграцию назад?»

В мире баз данных откат — это почти всегда ещё одна миграция вперёд, которая отменяет изменение (добавили колонку — новая миграция её удаляет). Автоматической «кнопки undo» для боевой базы нет намеренно: откат структуры часто означает потерю данных, и это должно быть осознанным шагом, а не нажатием клавиши. На стадии разработки, где данные не жалко, «откат» заменяется простым reset — снести всё и пересоздать.

Аналогия с gitМиграции ведут себя как коммиты: применённое не переписывают, ошибки чинят новым шагом поверх, а история — это правдивая летопись изменений, по которой любую базу можно привести в текущее состояние.

12Миграции в git и на сервере

Несколько практических следствий для командной работы — они станут актуальны после перехода на режим миграций (шаг 2 из раздела 7).

  • Файлы миграций коммитят в git. Они — часть кода. Создал миграцию локально — закоммитил вместе с изменением schema.prisma. Коллега, подтянув твой коммит, выполнит migrate dev и получит ту же форму базы.
  • На сервере — автоматически перед стартом. В скрипт деплоя добавляют prisma migrate deploy: перед запуском новой версии приложения он докатывает на боевую базу миграции, которых там ещё нет. Это безопасно и идемпотентно.
  • Конфликт миграций. Если двое одновременно создали миграции, после слияния веток база у одного из них окажется «впереди» истории. Обычно достаточно локального migrate dev — Prisma подскажет, что рассинхрон, а в dev можно пересоздать через reset. На боевой базе до такого не доводят — там история линейна.

13Типичные ошибки

ОшибкаЧто происходит и как правильно
Запустил db push на базе с миграциямиРассинхрон между файлами миграций и реальной формой базы. После перехода на миграции db push для этой базы не используют вовсе.
Запустил migrate dev на productionОн предназначен для разработки и может задавать вопросы/генерировать. На боевом — строго migrate deploy.
Отредактировал уже применённую миграциюРасходится «отпечаток» в _prisma_migrations. Исправление — всегда новой миграцией, а не правкой старой.
Удалил каталог migrations/ на проекте, который уже на миграцияхПотеря истории и рассинхрон с сервером. Удалять миграции можно только в dev до первого реального деплоя.
Соединил перенос данных и удаление старого в одной миграцииЕсли перенос не сработает — данные уже не вернуть. Делить на две миграции (раздел 10).
Забыл загрузить DATABASE_URLCLI Prisma не находит базу. В miracle все скрипты обёрнуты в dotenv-cli — запускать через npm run prisma:*, а не голой командой prisma.

  НЕТ (наш случай сейчас)  →  db push + reset, файлы миграций не нужны.
  ДА  →  режим миграций: migrate dev локально, migrate deploy на сервере.
    Изменение грозит стереть данные?  →  --create-only + правка SQL вручную (разделы 9–10).

Что делать прямо сейчас (пустая база)

npm run prisma:push     # изменил схему — синхронизировал базу
npm run prisma:reset    # база запуталась — пересоздать с нуля + тестовые данные
npm run prisma:studio   # посмотреть глазами, что лежит в таблицах

Учебная страница. Главная мысль: миграция — это записанный шаг изменения формы базы. Пока данных нет — шаги не записывают (db push); когда появляются ценные данные — каждый шаг сохраняют в файл и при необходимости правят руками, чтобы не потерять накопленное. Никакой магии: внутри — обычный SQL, который в 95% случаев Prisma пишет за вас.
