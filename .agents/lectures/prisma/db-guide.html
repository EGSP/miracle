После миграции с lowdb на Prisma меняется не только технология — меняется способ мышления о данных. Коллекции в памяти заменяются таблицами в PostgreSQL, синхронный API заменяется асинхронным, а вместо `db.collections.X.method()` теперь `prisma.x.prismaMethod()`. Это руководство показывает, как работать с новым слоем данных в контексте именно этого проекта.

1Как устроен PrismaService

PrismaService — единственная точка входа в базу данных. Он живёт в src/database/prisma.service.ts, зарегистрирован как @Global() провайдер и доступен в любом модуле без дополнительных импортов.

prisma.service.tsimport { Injectable, type OnModuleInit, type OnModuleDestroy } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
import pg from 'pg';
import { PrismaClient } from '../generated/prisma/client.js';
import { AppConfigService } from '../config/app-config.service.js';

@Injectable()
export class PrismaService extends PrismaClient
  implements OnModuleInit, OnModuleDestroy {

  constructor(config: AppConfigService) {
    // Prisma 7 требует driver adapter — подключаемся через пул соединений pg
    const pool = new pg.Pool({ connectionString: config.databaseUrl });
    const adapter = new PrismaPg(pool);
    super({ adapter });
  }

  async onModuleInit(): Promise<void> { await this.$connect(); }
  async onModuleDestroy(): Promise<void> { await this.$disconnect(); }
}

В сервисах домена инжектируется через конструктор:

constructor(private readonly prisma: PrismaService) {}

После инъекции у вас есть доступ ко всем таблицам через свойства клиента: this.prisma.user, this.prisma.order, this.prisma.fileContent и т.д. Имена свойств — camelCase от имени модели в схеме.

Почему extends PrismaClient, а не просто обёрткаНаследование от PrismaClient даёт всю типизацию клиента напрямую на PrismaService: IDE видит все модели и методы, TypeScript проверяет типы запросов и результатов. Если бы это была просто обёртка с полем client: PrismaClient, пришлось бы обращаться через this.prisma.client.user.

2Модели: схема и имена таблиц

Схема определена в back-nest/prisma/schema.prisma. Имя модели — Pascal Case (как в TypeScript). Имя таблицы в Postgres задаётся директивой @@map — snake_case, чтобы соответствовать SQL-соглашениям.

// Модель → таблица: PrismaClient-свойство = camelCase имени модели model User → prisma.user → таблица "users" model Session → prisma.session → таблица "sessions" model ProductType → prisma.productType → таблица "product_types" model File → prisma.file → таблица "files" model FileContent → prisma.fileContent → таблица "file_contents" model Order → prisma.order → таблица "orders" model TechnicalCondition → prisma.technicalCondition → "technical_conditions" model JobRun → prisma.jobRun → таблица "job_runs"

Каждая модель имеет стандартный набор полей. Поля createdAt/updatedAt проставляются Prisma автоматически — вручную их передавать не нужно.

// Стандартные поля у большинства моделей id String @id @default(uuid()) // Prisma генерирует uuid при create createdAt DateTime @default(now()) // ставится один раз при создании updatedAt DateTime @updatedAt // Prisma обновляет при каждом update deletedAt DateTime? // null = активна, дата = мягко удалена

3Граница типов: Prisma → @miracle/types

Это самый важный раздел для понимания архитектуры. Prisma генерирует собственные TypeScript-типы для каждой модели. Но возвращать эти типы из контроллера напрямую нельзя — из-за трёх причин:

  • генератор клиента на фронте не знает импортов из ../generated/prisma (он реэкспортирует только пакеты workspace);
  • Prisma-тип содержит password и другие backend-internal поля;
  • поля Json приходят как JsonValue (по сути unknown), а не как конкретный доменный тип.

Поэтому сервис работает с Prisma-типами внутри и возвращает типы из @miracle/types наружу.

// Внутри сервиса: Prisma-тип
const row = await this.prisma.user.findUnique({ where: { id } });
// row: { id: string, login: string, role: UserRole, password: string|null,
//        createdAt: Date, updatedAt: Date, deletedAt: Date|null }

// На границе: маппер убирает секретные поля → Stored<User>
private toPublic(row: { id: string; login: string; role: string;
    password: string | null; createdAt: Date; updatedAt: Date;
    deletedAt: Date | null }): Stored<User> {
  const { password: _password, ...rest } = row; // убираем поле
  return rest as Stored<User>;
}

// Контроллер возвращает Stored<User> с явной аннотацией (важно для кодогена)
getMe(@CurrentUser() user: AuthenticatedUser): Promise<Stored<User>> {
  return this.users.getPublicById(user.id);
}
Почему Date | string в DbEntityНа стороне Prisma поле createdAt — объект Date. На стороне фронта после HTTP-сериализации — ISO-строка. Тип Date | string в DbEntity покрывает оба случая честно. Фронт нормализует значение через new Date(value), который принимает и то, и другое.

4Чтение: findUnique, findFirst, findMany

Prisma предоставляет три метода чтения. Разница между ними принципиальная.

МетодКогда использоватьВозвращает
findUnique Поиск по @id или @unique полю. Гарантирует уникальность на уровне базы. T | null
findFirst Поиск по произвольному условию. Возвращает первую подходящую запись. T | null
findMany Список записей. Всегда возвращает массив, даже если результатов нет. T[] 
users.service.ts// findUnique — по первичному ключу (id). Если не найдено → null.
const user = await this.prisma.user.findUnique({ where: { id } });

// findFirst — по произвольному полю (login не @unique в нашей схеме)
const existing = await this.prisma.user.findFirst({ where: { login: dto.login } });

// findMany — список всех пользователей (без where → все записи)
const users = await this.prisma.user.findMany();
findUnique работает только с уникальными полямиЕсли передать в where поле, которое не помечено как @id или @unique в схеме — TypeScript выдаст ошибку компиляции. Для поиска по обычному полю используйте findFirst.

5Создание записи

Метод create принимает объект data. Поля id, createdAt, updatedAt не нужны — они задаются Prisma через директивы схемы. Исключение: id файла передаётся явно, потому что используется как имя файла на диске.

auth.service.ts// Обычное создание — id, createdAt, updatedAt Prisma проставляет сама
await this.prisma.user.create({
  data: {
    login: dto.login,
    password: hashedPassword,
    role: 'EMPLOYEE',           // значение enum как строка
  },
});

// Создание с явным id (files.service.ts) — нужно для имени файла на диске
const id = randomUUID();
const row = await this.prisma.file.create({
  data: { id, name, extension, bytes, authorId },   // id передаём явно
});

// Создание с nullable Json-полем
const row = await this.prisma.order.create({
  data: { authorId, fileId: fileId ?? null, details: undefined },
  // undefined → поле не передаётся → Prisma пишет NULL (поле nullable)
});
undefined vs null в dataPrisma трактует эти значения по-разному для nullable полей: null — явно записать NULL в базу; undefined — пропустить поле (для create используется default, для update поле не трогается). Это особенно важно для Json-полей.

6Обновление записи

Метод update требует уникальный идентификатор в where и обновляемые поля в data. Обновляются только переданные поля — остальные не трогаются (неглубокое слияние, в отличие от прежнего ts-deepmerge в lowdb).

product-types.service.ts// Обновление конкретных полей
const updated = await this.prisma.productType.update({
  where: { id },
  data: { name: dto.name },   // только name, synonyms не трогается
});

// Условное включение полей — антипаттерн через spread
const data: Record<string, unknown> = {};
if (dto.name !== undefined) data['name'] = dto.name;
if (dto.synonyms !== undefined) data['synonyms'] = dto.synonyms;

await this.prisma.productType.update({ where: { id }, data });
Spread-условия ломают типизацию PrismaПаттерн data: { ...(condition && { field: value }) } вызывает ошибку компиляции в строго-типизированном Prisma input. Правило: либо явно перечислять поля с проверкой на undefined, либо собирать объект Record<string, unknown> и приводить к типу (как в orders.service.ts). Первый способ предпочтительнее когда полей мало.

7Удаление: мягкое и жёсткое

В проекте используются оба вида удаления — в зависимости от модели.

Мягкое удаление (soft delete)

Запись остаётся в базе, но помечается датой. Используется для ProductType, FileContent, File — там, где нужна история или восстановление. Реализуется как обычный update:

product-types.service.ts// Пометить удалённым
await this.prisma.productType.update({
  where: { id },
  data: { deletedAt: new Date() },
});

// Снять пометку (восстановить)
await this.prisma.fileContent.update({
  where: { id: contentId },
  data: { deletedAt: null },
});

// При запросе — всегда фильтруем активные записи
const rows = await this.prisma.productType.findMany({
  where: { deletedAt: null },   // null = не удалено
});

Жёсткое удаление (hard delete)

Запись физически удаляется из базы. Используется для Session, JobRun:

files-content.service.ts// Жёсткое удаление по id
async delete(id: string): Promise<boolean> {
  try {
    await this.prisma.fileContent.delete({ where: { id } });
    return true;
  } catch {
    return false;   // запись не найдена — Prisma бросает ошибку
  }
}

// Удаление нескольких записей по условию (sessions.service.ts)
await this.prisma.session.deleteMany({
  where: { userId },   // удалить все сессии пользователя
});

8Фильтрация: where

Поле where принимает объект условий. Все перечисленные условия объединяются логическим AND.

orders.service.ts// Фильтр по нескольким полям (AND неявный)
const rows = await this.prisma.order.findMany({
  where: {
    authorId: query.authorId,   // только заказы этого пользователя
    fileId: query.fileId,       // и с конкретным файлом
  },
});

// Фильтр по enum-значению
const active = await this.prisma.jobRun.findFirst({
  where: {
    job: 'order-analyse',
    status: 'running',         // строка, совпадающая с enum-значением
  },
});

// Фильтр "в списке" (аналог SQL IN)
const rows = await this.prisma.jobRun.findMany({
  where: { status: { in: ['running', 'queued'] } },
});

// Активные записи: deletedAt IS NULL
const active = await this.prisma.productType.findMany({
  where: { deletedAt: null },
});

// Динамический фильтр: добавляем условия по мере необходимости
const where: Record<string, unknown> = {};
if (query.id !== undefined) where['id'] = query.id;
if (query.authorId !== undefined) where['authorId'] = query.authorId;
const rows = await this.prisma.order.findMany({ where });

Операторы сравнения

// Числовые сравнения
where: { bytes: { gte: 1024 } }          // >= 1024 байт
where: { bytes: { gt: 0, lt: 1048576 } }  // 0 < bytes < 1 MB

// Строковые операторы
where: { name: { contains: 'НЭМС' } }             // LIKE '%НЭМС%'
where: { name: { startsWith: 'ГОС' } }            // LIKE 'ГОС%'
where: { name: { contains: 'нэмс', mode: 'insensitive' } }  // без учёта регистра

// Инвертирование (NOT)
where: { deletedAt: { not: null } }    // только удалённые
where: { status: { not: 'cancelled' } }  // всё кроме cancelled

// Явный AND / OR / NOT
where: {
  OR: [{ authorId: userId }, { fileId: someFileId }],
}

9Сортировка: orderBy

files-content.service.ts// По одному полю — от новых к старым
const rows = await this.prisma.fileContent.findMany({
  where: { fileId, deletedAt: null },
  orderBy: { updatedAt: 'desc' },
});

// Динамическая сортировка (workers.service.ts)
const rows = await this.prisma.jobRun.findMany({
  where: query.status ? { status: query.status } : undefined,
  orderBy: query.sort === 'asc' || query.sort === 'desc'
    ? { createdAt: query.sort }
    : undefined,
});

// По нескольким полям (сначала по статусу, потом по дате)
orderBy: [
  { status: 'asc' },
  { createdAt: 'desc' },
]
Сортировка вместо .sort()Старый код lowdb сортировал массивы в памяти: .sort((a, b) => b.createdAt - a.createdAt). С Prisma сортировку выполняет PostgreSQL через orderBy — это эффективнее и корректнее для больших таблиц.

10Пагинация: skip и take

// Первые 20 записей (первая страница)
const page1 = await this.prisma.order.findMany({
  orderBy: { createdAt: 'desc' },
  take: 20,
});

// Вторая страница (пропустить первые 20)
const page2 = await this.prisma.order.findMany({
  orderBy: { createdAt: 'desc' },
  skip: 20,
  take: 20,
});

// Только одна запись — findFirst + orderBy эквивалентно findMany + take: 1
const latest = await this.prisma.session.findFirst({
  where: { refreshToken },
  orderBy: { createdAt: 'desc' },
});

11Чтение Json-полей

В проекте семь Json-колонок: Order.details, FileContent.content/meta, File.settings, TechnicalCondition.slotRules/displayTemplates, JobRun.input/output/memo/steps, ProductType.synonyms.

Prisma возвращает Json-поле как JsonValue (на практике это unknown). Чтобы получить конкретный тип, нужно приведение:

orders.service.ts// Читаем order.details из базы — тип JsonValue (unknown)
const order = await this.prisma.order.findUnique({ where: { id } });

// Приводим к доменному типу на границе чтения — не пересборка, только cast
const details = order?.details as OrderDetails | null;

// Дальше details типизирован и можно обращаться к полям
const hasRequirements = (details?.requirements ?? []).length > 0;
product-types.service.ts// synonyms хранится как jsonb массив строк
const found = rows.find((item) => {
  const synonyms = item.synonyms as string[];    // cast массива
  return synonyms.some((s) => this.normalizeName(s) === normalized);
});

12Запись и обновление Json-полей

При записи Prisma принимает любое JSON-сериализуемое значение. TypeScript требует явного приведения, поскольку тип JsonValue шире, чем конкретный объект:

files-content.service.ts// При обновлении — явный cast к object (Prisma принимает object для Json)
await this.prisma.fileContent.update({
  where: { id: data.id },
  data: {
    content: data.content as object[] | undefined,   // Content[]
    meta: data.meta as object | undefined,             // FileMeta
  },
});
job-runtime.service.ts// Сохранение рекурсивного дерева прогона
await this.prisma.jobRun.update({
  where: { id: root.id },
  data: {
    status: root.status as JobStatus,
    input: root.input !== undefined ? (root.input as object) : undefined,
    memo: root.memo !== undefined ? (root.memo as object) : undefined,
    steps: root.steps !== undefined ? (root.steps as object) : undefined,
  },
});
undefined vs null для Json (ещё раз — это важно)Для nullable Json-поля: undefined в поле data означает «не трогать поле» (для update) или «использовать default» (для create). null означает «явно записать NULL в базу». Паттерн value !== undefined ? (value as object) : undefined — стандартный способ условно обновить Json-поле.

13Фильтрация по содержимому Json

PostgreSQL поддерживает запросы внутрь jsonb-полей. Prisma открывает это через оператор path:

files.service.ts// Найти файлы с settings.isTechnicalCondition === true
const rows = await this.prisma.file.findMany({
  where: {
    settings: {
      path: ['isTechnicalCondition'],
      equals: true,
    },
  },
});
Когда Json-запросы не нужныБольшинство фильтраций по Json-полям в проекте делается в памяти (.find() после findMany()) — это проще и достаточно для нынешних объёмов. Json-запросы Prisma стоит использовать только когда нужно фильтровать миллионы записей или строить индекс по Json-полю. Для поиска синонимов в нескольких сотнях типов продукции in-memory поиск оптимален.

14Паттерн getOrThrow

Повторяющийся паттерн во всех сервисах: сначала пытаемся найти запись, потом бросаем исключение Nest, если не нашли.

Применяется везде: orders, product-types, tc, workers…// Базовый метод — возвращает null если не найдено
async get(id: string): Promise<Stored<Order> | null> {
  const row = await this.prisma.order.findUnique({ where: { id } });
  return row as Stored<Order> | null;
}

// Вариант с исключением — используется когда отсутствие = ошибка
async getOrThrow(id: string): Promise<Stored<Order>> {
  const order = await this.get(id);
  if (!order) {
    throw new NotFoundException('Заказ не найден');
  }
  return order;
}

// В методах, требующих существования — сначала проверяем, потом действуем
async update(id: string, patch: ...): Promise<Stored<Order>> {
  await this.getOrThrow(id);   // бросит 404 если не найдено
  const updated = await this.prisma.order.update({ where: { id }, data: ... });
  return updated as Stored<Order>;
}

15Паттерн мягкого удаления

Полный цикл работы с мягким удалением: создание → чтение только активных → пометка → восстановление.

files-content.service.ts — полный паттерн// 1. Создать запись — deletedAt не передаём, по умолчанию null
const row = await this.prisma.fileContent.create({ data });

// 2. Читать только активные — всегда фильтруем
const active = await this.prisma.fileContent.findMany({
  where: { fileId, deletedAt: null },   // ключевое условие
  orderBy: { updatedAt: 'desc' },
});

// 3. Иногда нужны все включая удалённые — передаём флаг
const all = await this.prisma.fileContent.findMany({
  where: {
    fileId,
    ...(includeDeleted ? {} : { deletedAt: null }),
  },
});

// 4. Мягко удалить / восстановить
await this.prisma.fileContent.update({
  where: { id: contentId },
  data: { deletedAt: mark ? new Date() : null },
});
Правило: фильтр deletedAt: null вездеЛюбой метод, возвращающий «активные» данные, обязан содержать where: { deletedAt: null }. Это не умолчание Prisma — база хранит все записи, и без этого фильтра мягко удалённые записи будут выглядеть как живые.

16Паттерн toPublic

Маппер, превращающий Prisma-результат в контрактный тип Stored<T>. Его задача: убрать backend-internal поля (прежде всего password) и при необходимости привести типы.

users.service.ts — канонический образец// Принимает сырой Prisma-объект, возвращает контрактный Stored<User>
private toPublic(user: {
  id: string; login: string; role: string;
  password: string | null; createdAt: Date;
  updatedAt: Date; deletedAt: Date | null;
}): Stored<User> {
  const { password: _password, ...rest } = user;   // убираем поле
  return rest as Stored<User>;
  // Note: даты не трогаем — Date присваивается Date|string автоматически
}
Более простые модели — без маппера, прямой cast// Когда нет секретных полей — достаточно приведения типа
const row = await this.prisma.order.create({ data });
return row as Stored<Order>;

// Для массивов
const rows = await this.prisma.productType.findMany({ where: { deletedAt: null } });
return rows as Stored<ProductType>[];
Когда нужен маппер, а когда достаточно castМаппер (toPublic) нужен только когда надо удалить поле из объекта в рантайме. Если поля не нужно удалять — простого as Stored<T> достаточно: TypeScript проверяет структуру, а лишние поля (которых нет в контрактном типе) тихо игнорируются сериализатором.

17Типичные ошибки и как их избежать

1. Забыть await

Ошибка

// TypeScript молчит — getOrThrow возвращает Promise
const order = this.orders.getOrThrow(id);
// order.details — ошибка в рантайме!
order.details?.productTypeId;

Правильно

const order = await this.orders.getOrThrow(id);
// теперь order — реальный объект
order.details?.productTypeId;

2. Вернуть Promise из контроллера без явной аннотации

Проблема

// Без аннотации генератор клиента выведет тип сам
// и может получить import("../generated/prisma")
list() {
  return this.orders.getOrders(query);
}

Правильно

// Явная аннотация → генератор видит Stored<Order>
list(): Promise<Stored<Order>[]> {
  return this.orders.getOrders(query);
}

3. Вернуть Prisma-тип из контроллера напрямую

Ошибка

// Prisma-тип утекает наружу — генератор сломается
async getOne(id: string) {
  return this.prisma.user.findUnique({ where: { id } });
  // тип: { id, login, password, ... } из generated/prisma
}

Правильно

// Сервис делает маппинг, контроллер возвращает контрактный тип
async getOne(id: string): Promise<Stored<User>> {
  return this.users.getPublicById(id);
}

4. Потерять null при мягком удалении

Ошибка

// Нет фильтра → вернёт и удалённые
const types = await this.prisma.productType.findMany();

Правильно

// Всегда фильтруем активные
const types = await this.prisma.productType.findMany({
  where: { deletedAt: null },
});

5. Передать spread с условными полями в data

Ошибка компиляции

// TypeScript: объект не совместим с типом Prisma input
await prisma.order.update({
  where: { id },
  data: {
    ...(patch.fileId && { fileId: patch.fileId }),
  },
});

Правильно

const data: Record<string, unknown> = {};
if (patch.fileId !== undefined) data['fileId'] = patch.fileId;

await prisma.order.update({
  where: { id },
  data: data as Parameters<typeof prisma.order.update>[0]['data'],
});

6. Читать Json-поле без приведения типа

TypeScript-ошибка

// details: JsonValue (unknown) — нельзя обратиться к полям
const order = await prisma.order.findUnique({ where: { id } });
order.details.requirements; // ошибка!

Правильно

// Явный cast на границе чтения
const details = order?.details as OrderDetails | null;
details?.requirements;  // работает ✓
