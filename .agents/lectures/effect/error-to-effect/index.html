Ошибки в Effect: failure, defect и durable jobs

Хорошая обработка ошибок в Effect начинается не с большой иерархии классов, а с выбора правильного канала. Операционная ошибка внешнего мира должна стать failure, дефект программы остаётся defect, а отмена job не должна выглядеть как падение.

1Каналы завершения Effect

У Effect не один «throw», а несколько способов завершиться. Это важно для job-движка, потому что разные каналы ловятся разными комбинаторами.

КаналСмыслЧем ловить
SuccessОбычный результат A.Композиция продолжается.
FailureОжидаемая ошибка E: сеть, БД, невалидный ответ, доменный gate.catchAll, mapError, either.
DefectНеожиданный дефект: нарушенный инвариант, throw там, где его не обещали.catchAllCause, tapErrorCause, sandbox.
InterruptionВолокно прервали, например через cancel.Обрабатывать отдельно; это не failed job.

2Почему Effect.promise должен быть редким

Effect.promise подходит только для промиса, который по контракту не должен отклоняться. Если он всё же reject-ится, отказ попадает в defect-канал. Такой defect не поймают catchAll, mapError и tapError.

ПравилоSDK, HTTP, Prisma, файловая система, JSON/Zod и любые сервисные вызовы, которые могут упасть, заворачиваются через Effect.tryPromise({ try, catch }).
// Плохо для падающего внешнего вызова: reject станет defect.
const user = yield* Effect.promise(() => users.get(id));

// Хорошо: reject станет failure и его увидит catchAll/mapError.
const user = yield* Effect.tryPromise({
  try: () => users.get(id),
  catch: (error) => new Error(`load user "${id}": ${formatUnknown(error)}`, { cause: error }),
});

3Почему tryPromise без catch даёт UnknownException

Одноаргументный Effect.tryPromise(fn) переводит reject в failure, но если причина неизвестной формы, Effect создаёт служебный UnknownException. Его сообщение часто выглядит так:

An unknown error occurred in Effect.tryPromise

Настоящая причина может лежать в cause. Поэтому на границе с внешним миром лучше всегда давать свой catch и понятный label.

4Минимальные helper-ы

В большинстве мест достаточно обычного Error с сохранённым cause. Главное — не потерять исходную ошибку и добавить короткий контекст.

const formatUnknown = (error: unknown): string => {
  if (error instanceof Error) {
    const cause = error.cause ? `; cause: ${formatUnknown(error.cause)}` : '';
    return `${error.name}: ${error.message}${cause}`;
  }
  if (typeof error === 'string') return error;
  try { return JSON.stringify(error); }
  catch { return String(error); }
};

const tryLabeledPromise = <Value>(label: string, promise: () => Promise<Value>) =>
  Effect.tryPromise({
    try: promise,
    catch: (error) => new Error(`${label}: ${formatUnknown(error)}`, { cause: error }),
  });

5Контекст через mapError

Нижний слой знает техническую причину: какой SDK-вызов, какой operation id, какая БД-операция. Job знает бизнес-контекст: applicationId, chunkKey, fileId, tcId. Эти уровни должны наращивать цепочку причин, а не заменять её.

Effect.gen(function* () {
  const catalog = yield* tryLabeledPromise(
    'загрузка каталога типов продукции',
    () => productTypes.getAll(),
  );

  const opId = yield* submitOnce(() => yandex.submitCompletion(request), {
    label: `extract positions submit; chunk=${input.chunkKey ?? 'unknown'}`,
    extraMemo: { finalPrompt },
  });

  return yield* pollUntilDone(() => yandex.pollCompletionJson(opId, schema), {
    label: `extract positions poll; opId=${opId}`,
  });
}).pipe(
  Effect.mapError(
    (error) => new Error(
      `failed to extract positions from chunk "${input.chunkKey ?? 'unknown'}"`,
      { cause: error },
    ),
  ),
);

6tapError, catchAll и catchAllCause

tapError нужен для сайд-эффектов: лог, запись статуса, метрика. Он не меняет ошибку. catchAll нужен только когда ошибка действительно обработана: есть fallback, retry, компенсация или best-effort пропуск. Если нужно видеть defects и interruption, работайте с cause через catchAllCause или tapErrorCause.

// Best-effort: ошибка ребёнка обработана, родитель идёт дальше.
jobs.run(childJob, key, input).pipe(
  Effect.catchAll((error) =>
    Effect.logWarning(`child skipped: ${formatUnknown(error)}`),
  ),
);

7Durable runtime jobs

Runtime обязан сохранять результат падения даже если внутри случился defect. Но interruption от cancel не должен становиться failed-статусом.

return body.pipe(
  Effect.tapErrorCause((cause) =>
    Cause.isInterruptedOnly(cause)
      ? Effect.void
      : Effect.promise(() =>
          store.patch(node.id, {
            status: 'failed',
            error: errToMessage(Cause.squash(cause)),
          }),
        ),
  ),
);
Практика для UI и логовВ JobRun.error лучше хранить компактную человекочитаемую цепочку причин. Полный Cause.pretty(cause) со стеком и fiber-деталями отправляйте в backend logs.

8Когда нужны typed errors

Typed errors полезны, когда по типу ошибки есть поведение: retry только для poll, игнорировать not found, показать пользователю отдельную категорию, сделать catchTag. Если код нигде не ветвится по типу, большая иерархия ошибок только усложнит чтение.

// Достаточный дефолт для диагностики:
new Error('Yandex poll failed', { cause: error });

// TaggedError уместен, когда ниже есть catchTag('YandexPollError').
Короткая формула: падающий внешний вызов → labeled tryPromise; каждый значимый слой добавляет контекст через mapError; runtime сохраняет cause и не путает cancel с failure.
